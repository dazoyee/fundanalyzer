# 四半期分析の有効活用可否 調査レポート

> 調査日: 2026-07-17
> 調査範囲: ローカルソースコード（develop ブランチ）、docs/notes・docs/plans・docs/research、Web一次資料（EDINET API仕様書・金融庁EDINETタクソノミ資料・JPX公表資料）
> 調査方法: コード調査は独立した2回の探索で相互照合し、差異はコード直読で解消。Web調査は一次資料（公式PDF）確認＋独立エージェントによる裏取りを実施

## サマリー

- 四半期報告書（書類種別140/150）は**スクレイピング・企業価値算出・保存まではされているが、集計・投資指標・グラフ・RIM・割安判定のいずれにも使われていない**。唯一 `/v3/corporate` の分析結果テーブルにだけ生データが表示される非対称な状態にある。
- 根本的な制約として、**四半期報告書は金商法改正（2024年4月1日以後開始事業年度から適用）で廃止済み**であり、EDINET への新規流入は既に止まっている。第1・第3四半期の財務情報は取引所規則に基づく決算短信（TDnet）に一本化され、EDINET では開示されない。
- 後継の**半期報告書（書類種別160/170）は enum 定義のみで完全に未対応**。scraping/view いずれの設定にも含まれず、収集・分析・表示のどの経路にも乗らない。アプリの日次バッチは書類一覧を種別を問わず全件 DB 登録する仕組みのため、半期報告書のメタデータは既に `document` テーブルに蓄積されている可能性が高い（本番DB実測が必要）。その場合、遡及処理は一覧APIの再取得なしで `POST /v1/scrape/date` の日付ループのみで実現できる。
- **「四半期の有効活用」は、単独では成立しない。** 新規データが制度上流入しないため、改善の本命は「半期報告書対応（＋制度移行以降の遡及取得）」であり、過去の四半期データはその文脈で（時系列の連続性を保つ材料として）活きる。
- 決算短信（TDnet）による四半期粒度の補完は技術的には可能だが、公式APIは有料（法人向けTDnet API、または個人向けJ-Quants APIアドオン）、無料の閲覧サービスは掲載期間約31日・利用規約上の懸念があり、**新規外部I/O・東証タクソノミ対応を要する別規模のタスク**。今回の実装スコープからは除外し将来課題とするのが妥当。

## 調査背景・目的

「四半期の分析が有効活用できていない」という問題意識を起点に、①鮮度への活用（四半期/半期データを最新の企業価値評価・集計・グラフ・RIMへ反映）、②半期報告書対応、③表示の非対称性解消、④そもそも四半期処理が不要かの見極め、の4観点をフラットに評価し、改善方針の判断材料（Gate 1 の入力）を提供する。

## 主要な発見事項

### 1. 四半期データの現在の流れ — 「計算するが使わない」

3つの設定値が独立に効いており、処理段階ごとに対象範囲が異なる。

| 設定キー（application.yml） | 値 | 用途 |
|---|---|---|
| `app.config.scraping.document-type-code` | `120,130,140,150` | スクレイピング・分析（`analysis_result` 保存）対象 |
| `app.config.view.document-type-code` | `120,130` | 集計（平均・標準偏差・割安判定）・投資指標・グラフ・RIM の対象 |
| `app.config.remove-document.document-type-code` | `140,150` | BS/PL が取得できなかった四半期書類を処理対象外へ倒す除外設定 |

- **事実**: 140/150 はスクレイピングされ `analysis_result` に保存される。`AnalyzeInteractor.analyze` に書類種別フィルタはなく、四半期も無条件で企業価値算出・保存される。
  *出典: `DocumentSpecification.java:56-57`、`AnalyzeInteractor.java`（analyze メソッド）*
- **事実**: 集計・投資指標には一切流入しない。`AnalysisResultSpecification` が `view.document-type-code`（120,130）で絞り込み、`AnalyzeInteractor.indicate` も同設定で 140/150 を早期リターンするため、`investment_indicator` に四半期由来の行は生成されない。
  *出典: `AnalysisResultSpecification.java:41-42,72,180,206,227,267`、`AnalyzeInteractor.java`（indicate メソッド）*
- **事実**: `/v3/corporate` では非対称な表示になっている。分析結果テーブルは無フィルタの `analysisResults`（scraping 設定バインドの `ViewCorporateInteractor.targetTypeCodes` 由来）で四半期行を表示する一方、企業価値グラフ（`analysisChartAll` ← `analysisLabelAll`/`analysisPointAll`）・RIM理論株価・2モデル合意度は `CorporatePresenter.targetTypeCodes`（view 設定バインド）で 120/130 に絞られる。
  *出典: `ViewCorporateInteractor.java:85-86,264-275`、`CorporatePresenter.java:41-42,139-140,176-195`、`corporate-v2.html:339-373,770-787`*
- **事実**: `/v3/index` には「四半期」タブ（`Target.QUART`）があり、最新提出書類が 140/150 の企業を一覧表示する。ただし表示内容は企業一覧の絞り込みであり、四半期の財務指標の集計ではない。
  *出典: `web/presenter/Target.java:7`、`ViewCorporateInteractor.viewQuart()`（126-148行）、`index-v2.html:145-152`*
- **含意**: 「表には出るが、どの判断材料（割安判定・指標・グラフ）にも使われない」状態であり、利用者は四半期の値をどう解釈すべきか判断できない。ドキュメント上の「四半期はどの画面にも流入しない」という過去の前提（quarterly-annualization-fix.md）は、テーブル表示に関しては不正確だった。

### 2. 分析ロジック上の四半期の扱い — 年換算は修正済み、指標は限定的

- **事実**: 企業価値算出は営業利益のみ `QuarterType` の weight（Q1=1〜Q4=4）で年換算（÷weight×4）し、BSストック項目は等倍。BS項目まで年換算していた理論的欠陥は修正済み（コミット `54d3ed2a`）。
  *出典: `AnalysisResult.java:182-241`、`docs/notes/T20260713-gate1-production-analysis-fixes.md`（P4）*
- **事実**: 四半期書類では EPS/ROE/ROA は算出せず `Optional.empty()` を返す（BPS と企業価値のみ算出）。
  *出典: `AnalysisResult.java`（calculateEps/Roe/Roa、268-340行）*
- **事実**: 修正前の式で保存された四半期の `analysis_result` 約38,913件は再計算せず放置する方針（案B）が Gate 1 承認済み。当時の判断理由は「集計・表示に構造的に流入しないため実害がない」。
  *出典: `docs/plans/quarterly-annualization-fix.md` §5・§9、`docs/notes/T20260713-gate1-production-analysis-fixes.md`*
- **含意**: 四半期データを view 側で活用する方針に転換する場合、修正前の誤った値が表示・集計へ流入するため、**全期間再計算が前提条件になる**（「新旧混在を許容しない」というリポジトリの設計判断とも整合）。再計算基盤は `POST /v1/admin/analysis/recalculate` として実装・本番実行実績あり（EDINETアクセス不要・DB内再計算のみ）。
  *出典: `AnalysisController.java:88-123`、`AnalyzeInteractor.java:265-365`、`docs/notes/T20260716-model-validation-recalc-phase1c-phase2.md`*

### 3. 制度上の制約 — 四半期報告書は廃止済み、新規データは半期報告書のみ

- **事実**: 金商法改正により四半期報告書制度は廃止（2024年4月1日施行、同日以後開始する事業年度から適用）。上場会社（特定事業会社以外）は中間会計期間経過後45日以内に半期報告書を提出する。
  *出典: 金融庁・KPMG/EY/森濱田松本の改正解説、実提出例（リンナイ 2024-11-13 提出の半期報告書）*
- **事実**: EDINET API の書類種別コードは 160=半期報告書、170=訂正半期報告書（EDINET API仕様書 Version 2 の書類種別コード表で確認）。
  *出典: EDINET API仕様書（ESE140206.pdf）p.87-88*
- **事実**: 半期報告書の様式（第四号の三様式）は旧四半期報告書の様式を基本的に踏襲し、中間連結財務諸表（中間連結貸借対照表・中間連結損益計算書・中間連結キャッシュ・フロー計算書）を含む。ただし XBRL タクソノミ要素は「旧四半期の要素を廃止し、中間財務諸表の要素を新規追加」であり、タグレベルの完全互換ではない。
  *出典: 金融庁「EDINETタクソノミの概要説明」(2024年11月版)、「2025年版EDINETタクソノミ更新概要」*
- **事実**: 第1・第3四半期の財務情報は取引所規則に基づく四半期決算短信（TDnet）に一本化され、EDINET では開示されない。
  *出典: PwC/JPX FAQ/JICPA の制度解説*
- **含意**: 「四半期の有効活用」を EDINET の範囲で考える場合、**対象は (a) 過去に蓄積した四半期データ、(b) 今後の半期報告書、の2つ**しかない。半期対応をしない限り、中間期の財務データは恒久的に取得できない。

### 4. 半期報告書（160/170）対応のギャップ — enum 定義のみ、必要な変更点は明確

- **事実**: `DocumentTypeCode.DTC_160/DTC_170` は定義済みだが、scraping/view いずれの設定にも含まれず、コード全文 grep で機能的な参照はゼロ。
  *出典: `DocumentTypeCode.java:27-28`、`application.yml:209,218,248`（application-prod.yml にオーバーライドなし）*
- **事実**: `QuarterType` は `docDescription` の「期第◯四半期(」パターンで判定するため、半期報告書は `QT_OTHER`（weight=null → 年間扱い）になる。半期の営業利益を年換算する weight=2 相当の定義が必要。設計上は「重み定義を追加するだけで同じ式が使える」ことが既に確認されている。
  *出典: `QuarterType.java:37-47`、`AnalysisResult.java:182-241`、`docs/plans/quarterly-annualization-fix.md` §7*
- **事実**: 財務諸表の特定は `scraping_keyword` マスタ（XBRL TextBlock 要素名）で行う。四半期用要素（`jpcrp_cor:QuarterlyConsolidatedBalanceSheetTextBlock` 等）は登録済みだが、中間財務諸表用の要素は未登録。半期対応には中間財務諸表の TextBlock 要素を追加する Flyway マイグレーションが必要。
  *出典: `db/dataset/V1.0.0__init_insert.sql:53-60`、`ScrapingKeywordDao` / `XbrlScraping.java`*
- **事実**: `financial_statement`・`analysis_result` の `quarter_type` 列には CHECK 制約（'1'〜'4'）がある。半期をどの値で表現するか（例: 累計2四半期と等価な '2' の再利用、または制約拡張）は設計判断が必要。
  *出典: `db/migration/V0.1.0__init_create.sql:139,159`*
- **事実**: `ViewSpecification.isAnnualOrSemiAnnualReport` は名前に反して 120/130 のみ判定しており、160/170 対応時に誤用されるリスクがある。
  *出典: `ViewSpecification.java:329-332`*
- **含意**: 半期対応の技術的ギャップは「設定2箇所＋QuarterType拡張＋scraping_keyword追加＋CHECK制約の扱い＋命名整理」に収まり、既存の四半期処理パイプラインをほぼそのまま再利用できる。実装規模は中程度。

### 5. 遡及取得の実現性 — 既存機構で可能、一覧は再取得不要の可能性が高い

- **事実**: 書類一覧の取り込み（`DocumentSpecification.insert` / `EdinetDocumentSpecification`）は docTypeCode を問わず EDINET が返した全件を登録する。アプリが日次稼働していた期間の半期報告書メタデータは既に `document`/`edinet_document` に登録済みの可能性が高い（本番DB実測が必要）。
  *出典: `DocumentSpecification.java:250-258`、`EdinetDocumentSpecification.java:146-154`*
- **事実**: 過去日付の処理手段は複数実装済み。一覧が登録済みなら `POST /v1/scrape/date`（同期・list API 不要、acquisition のみ）を日付ループするのが最小コスト。未登録なら `POST /v2/edinet-list`（日付範囲対応）で一覧を先に取り込める。
  *出典: `AnalysisController.java:131-135`、`EdinetController.java:74-78`、`DocumentInteractor.java:138-252`*
- **事実**: EDINET のレートリミッタは 6回/3秒（≒2 req/秒）。所要時間は概ね「対象書類数 × 0.5秒」。上場企業約4千社 × 年1回 × 約2年分 ≈ 最大8千件程度と見込まれ、ダウンロードだけなら1〜2時間オーダー。サーキットブレーカー OPEN 時（全呼び出し失敗が20回続いた場合）は300秒停止が加算される。
  *出典: `application.yml:66-76,118-138`*
- **事実**: 重複はユニークキー＋`UniqueConstraintException` 捕捉で安全にスキップされる。既知の懸念は、過去に全項目 ERROR となり `removed` 化された書類の扱いと、`remove-document.document-type-code`（140,150限定）が半期に適用されない点（適用したい場合は設定追加が必要）。
  *出典: `DocumentSpecification.java:269-285`、`DocumentInteractor.java:444-446,509-579`*

### 6. 決算短信（TDnet）の実現性評価 — 技術的に可能だが別規模のタスク

- **事実**: 公式取得手段は有料のみ。法人向け TDnet API（基本料7万円＋従量）、または個人向け J-Quants API の適時開示アドオン（月額11,000円税込）。無料の適時開示情報閲覧サービスは掲載期間が開示日を含め31日間で、過去分の遡及取得はできない。
  *出典: JPX「TDnet API」公式ページ、JPX ニュースリリース（J-Quants 適時開示アドオン）*
- **事実**: 決算短信の添付資料（連結財務諸表）は連結財規の様式に従うため、本アプリが必要とする BS/PL 項目（流動資産・投資その他の資産・流動負債・固定負債・営業利益・当期純利益・純資産・自己株式・発行済株式数）は XBRL から取得可能。ただし東証タクソノミ（EDINET とは別体系）であり、`scraping_keyword` の仕組みをそのまま流用できるかは別途検証が必要。
  *出典: JPX「決算短信・四半期決算短信 作成要領」*
- **含意**: 第1・第3四半期の粒度を取り戻す唯一の手段だが、新規外部I/O（クライアント・Resilience4j 設定・認証/課金）＋東証タクソノミ対応＋保管期間制約への対応が必要で、EDINET 内の改善とは独立した別規模のタスク。今回の実装スコープから除外し、将来課題として切り出すのが妥当。

## 4観点の評価

| 観点 | 評価 | 根拠 |
|---|---|---|
| ① 鮮度への活用 | **有効。ただし「四半期」ではなく「半期」が主役** | 有報間の空白（最大約1年）を中間データで埋める価値はある。ただし新規流入は半期報告書のみのため、半期対応とセットでなければ過去データにしか効かない。集計への混ぜ方は設計判断が必要（発見事項1・2） |
| ② 半期報告書対応 | **最優先。これをしない限り中間期データは恒久的にゼロ** | 制度上、EDINET の中間期データは半期報告書のみ（発見事項3）。技術ギャップは明確で既存パイプラインを再利用できる（発見事項4）。遡及取得も既存機構で可能（発見事項5） |
| ③ 表示の非対称性解消 | **必要。方針①②の設計に従属** | テーブルだけに出る現状は解釈不能な UI。①②の「中間データをどう見せるか」の設計に含めて解消するのが自然（発見事項1） |
| ④ そもそも不要かの見極め | **「全部やめる」は不合理。ただし現状維持も中途半端** | scraping 対象維持の追加コストはほぼゼロ（新規流入が止まっているため）。一方、活用しないなら保存済み約3.9万件と表示の非対称だけが残る。「活用する」か「表示からも外す」かの二択であり、放置が最も価値が低い |

## 改善オプション

- **案A（半期対応＋活用）**: 160/170 を scraping・view 両方の対象に追加し、QuarterType 拡張・scraping_keyword 追加・遡及取得・全期間再計算・画面表示設計（中間データの区別表示）まで行う。中間期の鮮度が判断材料に反映される。実装規模: 中。
- **案B（半期対応のみ・活用は最小限）**: 160/170 を scraping 対象にのみ追加しデータ蓄積を再開する。view への反映は見送り、表示の非対称は「テーブルからも中間データを外す」ことで解消。実装規模: 小。鮮度改善は得られない。
- **案C（現状維持＋整合性修正のみ）**: 設定は触らず、テーブル表示から 140/150 を外して非対称だけ解消。実装規模: 極小。中間期データは恒久的に欠落したまま。
- **案D（四半期の後始末のみ）**: 140/150 を scraping 対象から外し、保存済み四半期データも表示から排除。半期非対応。実装規模: 極小。情報量は最も減る。

推奨は **案A**。理由: ②の評価どおり半期対応は待つほど欠落期間が広がる一方、技術ギャップが小さく既存資産（四半期パイプライン・再計算基盤・遡及機構）をそのまま活かせるため、投資対効果が最も高い。案Aの中の「集計への混ぜ方」（平均・標準偏差に中間データを混ぜるか、最新値・グラフ表示に限定するか）は Gate 1 で方針決定する。
