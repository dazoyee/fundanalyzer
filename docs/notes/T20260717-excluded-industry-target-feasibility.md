# 調査ノート: 分析・スクレイピング対象外業種の対象化可否

- ステータス: 調査（コード変更なし）
- 起票理由: `app.config.scraping.no-industry` で処理対象外としている業種（銀行業・保険業ほか）を分析・スクレイピング対象に加えられるかの実現可能性調査。技術面（XBRLスクレイピング可否）とモデル面（企業価値算出モデルの適用可否）の両面を、実際の有価証券報告書XBRLで検証した。

---

## 1. 結論サマリ

| 観点 | 結論 |
|---|---|
| 銀行業・保険業以外の7カテゴリ | **対象化の実益なし**（上場発行者がほぼ存在しない。§3） |
| 銀行業・保険業のファイル特定・株式総数 | **既存機構のまま動作する**（標準TextBlockを使用。§4.1） |
| 銀行業・保険業のBS/PL科目抽出 | **現行の科目マスタでは大半が取得不能**（業法様式のラベル差異。§4.2） |
| 現行企業価値モデルの適用 | **構造的に不可能**（必須6値のうち5値が財務諸表様式上存在しない。§5） |
| 総合 | `no-industry` から外すだけの対象化は不可。**専用モデルの追加（または RIM 系のみの評価）＋科目マスタ拡充が必須**（§6） |

## 2. 現状の除外の実装

除外は `application.yml` の `app.config.scraping.no-industry`（`src/main/resources/application.yml` の `scraping.no-industry`）に業種名9カテゴリを列挙し、`IndustrySpecification.isTarget()`（`domain/domain/specification/IndustrySpecification.java:125-130`）が業種IDで判定する。利用箇所は3つ。

| 利用箇所 | 効果 |
|---|---|
| `DocumentSpecification.findTargetList()` → `isTarget`（`DocumentSpecification.java:546,608-611`） | 処理対象書類リストから除外。**ダウンロード・スクレイピング・分析のすべてがこのリスト起点**のため、除外業種はXBRLのダウンロード自体が行われない |
| `CompanySpecification`（`CompanySpecification.java:214`） | 対象企業リスト（株価取得等の起点）から除外 |
| `DistributionInteractor`（`DistributionInteractor.java:62`） | 業種別分布の集計から除外 |

ダウンロード前にフィルタされるため、本番サーバの `decode` ツリーにも銀行・保険のXBRLは存在しない（主要行・大手保険6社のEDINETコードでファイル名検索し不存在を確認）。

## 3. 除外9カテゴリの内訳と対象化の実益

EDINETコードリスト（`EdinetcodeDlInfo.csv`、提出者業種列）で上場発行者数を集計した。

| 業種名（no-industry記載値） | 発行者数 | うち上場 |
|---|---|---|
| 銀行業 | 134 | **83** |
| 保険業 | 35 | **14** |
| 内国法人・組合（有価証券報告書等の提出義務者以外） | 1,968 | 0 |
| 外国法人・組合 | 185 | 3 |
| 外国法人・組合（有価証券報告書等の提出義務者以外） | 632 | 0 |
| 外国政府等 | 37 | 0 |
| 個人（組合発行者を除く） | 2,933 | 0 |
| 個人（非居住者）（組合発行者を除く） | 86 | 0 |
| その他（仮登録用） | 0 | 0 |

- 銀行業・保険業以外は実質「業種」ではなく提出者区分であり、上場株式を持たないため対象化しても分析対象にならない（`no-company` と同様の防御的除外として妥当）。
- 業種「外国法人・組合」の上場3社はJDR型の外国法人で、有報様式も国内基準と異なるため個別論点。実益は僅少。
- **対象化の実益があるのは銀行業（上場83社）・保険業（上場14社）の計97社のみ。**
- 補足: 提出者**種別**が外国法人・組合でも提出者**業種**が一般業種（建設業・医薬品等）の上場企業が存在する。これらは業種フィルタでは除外されておらず、既に処理対象である。

## 4. 技術面調査（実XBRL検証）

検証サンプル（EDINET書類閲覧サイトから取得した提出書類の本文htm。ixbrl属性を保持）:

| 発行者 | 類型 | docID |
|---|---|---|
| 三菱UFJフィナンシャル・グループ（E03606） | 銀行業・持株会社 | S100YJQO |
| 七十七銀行（E03545） | 銀行業・銀行本体（地銀） | S100YAM0 |
| 東京海上ホールディングス（E03847） | 保険業・持株会社（連結IFRS） | S100YLS8 |

### 4.1 ファイル特定と株式総数 — 既存機構で動作する

- `ScrapingInteractor.findTargetFile()` → `XbrlScraping.findFile()`（`XbrlScraping.java:45-96`）は、honbunファイル中の `name` 属性（XBRLのTextBlock要素名）と `scraping_keyword` の照合でファイルを特定する。
- 銀行の連結BS/PLも標準要素 `jpcrp_cor:ConsolidatedBalanceSheetTextBlock` / `jpcrp_cor:ConsolidatedStatementOfIncomeTextBlock` を使用しており（3社の実htmで確認）、いずれも `scraping_keyword` に登録済み。**ファイル特定はそのまま成功する。**
- 東京海上の連結（IFRS）も `jpigp_cor:ConsolidatedStatementOfFinancialPositionIFRSTextBlock` 等を使用しており、これも登録済み。
- 株式総数の `jpcrp_cor:IssuedSharesTotalNumberOfSharesEtcTextBlock` は3社とも存在。**株式総数の取得は業種非依存で成立する。**

### 4.2 科目抽出 — 業法様式のラベル差異で大半が取得不能

科目は `SubjectSpecification.findBsSubject/findPlSubject`（`SubjectSpecification.java:44-49,76-81`）が `bs_subject` / `pl_subject` の科目名と**完全一致**で照合し、不一致行は黙って捨てられる（`ScrapingInteractor.java:161-171,193-203`）。実htmの科目ラベル出現状況:

| ラベル | 銀行連結BS/PL | 銀行本体の単体 | 持株会社の単体 | 保険連結(IFRS) |
|---|---|---|---|---|
| 流動資産合計 | ✕ | ✕ | ○ | ✕ |
| 流動負債合計 | ✕ | ✕ | ○ | ✕ |
| 固定負債合計 | ✕ | ✕ | ○ | ✕ |
| 投資その他の資産合計 | ✕ | ✕ | ○ | ✕ |
| 営業利益 | ✕ | ✕ | ○ | ✕ |
| 純資産合計 | ✕（「純資産の部合計」） | ✕（同左） | ○ | ✕（「資本合計」） |
| 資産合計 | ✕（「資産の部合計」） | ✕（同左） | ○ | ○ |
| 経常収益・経常費用・経常利益 | ○ | ○ | －（営業収益様式） | ✕ |
| 当期純利益（親会社帰属含む） | ○ | ○ | ○ | ✕（「当期利益」） |

- 銀行様式（銀行法施行規則）のBSは流動/固定の**無区分**で、部単位の合計ラベル（資産の部合計・負債の部合計・純資産の部合計）を使う。PLは経常収益/経常費用様式で**営業利益が存在しない**。
- 東京海上の連結はIFRS（流動性配列・保険サービス様式）で、国内様式のラベルはさらに乖離する。大手保険は IFRS 採用が広がっており、保険業の対象化ではjpigp様式対応が実質必須になる。
- 持株会社の**単体**財務諸表（0105310/0105020）は一般事業会社様式であり、現行モデルの必須値がすべて揃う。ただしアプリは連結優先（`scraping_keyword.priority`）の設計であり、銀行本体上場（地銀の大半）は単体も銀行様式のため、単体流用では83社中の持株会社型しかカバーできない。

## 5. モデル面調査（企業価値算出モデルの適用可否）

`AnalysisResult.calculateCorporateValue()`（`domain/value/AnalysisResult.java:182-241`）は次の6値を必須とし、欠損時は `FundanalyzerNotExistException` を送出する:

> 流動資産合計・投資その他の資産合計・流動負債合計・固定負債合計・営業利益・株式総数

- 銀行・保険（連結）はこのうち**株式総数以外の5値が財務諸表様式上存在しない**。ラベルのマッピング追加で救える問題ではなく、流動/固定区分や営業利益という概念自体が業法様式にない。
- 現行モデルの式（営業利益×倍率＋流動資産−流動負債×係数＋投資その他の資産−固定負債）は運転資本ベースの事業会社モデルであり、預金・保険契約準備金を負債の主体とする銀行・保険には**理論的にも適用不能**。
- 業種係数自体は `industry` マスタに銀行業・保険業とも設定済み（`V0.4.0__update_industry_coefficient.sql`）であり、係数はブロッカーではない。
- 一方、**RIM（残余利益モデル）系は適用可能性がある**: `calculateRimValue`（同 `:141-149`）の入力は BPS×ROE÷資本コスト、すなわち純資産・当期純利益・株式総数のみ。銀行・保険とも「純資産の部合計」「当期純利益」ラベルを `bs_subject`/`pl_subject` に追加すれば計算材料は揃う。
- ただし現行実装は `AnalysisResult` コンストラクタ（同 `:69-78`）で corporate_value の算出が先に走り、失敗すると行自体が保存されないため、「RIMだけ算出して保存する」経路が存在しない。valuation（割引値・割引率）・corporate_view の集計も corporate_value 前提であり、RIMのみの企業を許容するには null 耐性の設計変更が要る。

## 6. 対象化する場合の選択肢と必要な実装

### 選択肢

| 案 | 概要 | 評価 |
|---|---|---|
| A. 銀行・保険専用モデルの追加 | 経常利益（銀行・保険の実質本業利益）×倍率＋純資産ベースの専用式を業種で分岐 | 全97社をカバーできるが、モデル設計・検証の作業量が最大 |
| B. RIM系のみで評価 | corporate_value を算出せず rim_value・BPS/EPS/ROE/ROA のみ算出・表示 | 科目ラベル追加＋null耐性化で実現可能。valuation（割引率）系は対象外のまま |
| C. 持株会社は単体財務諸表で現行モデル | 連結優先を業種条件で単体優先に切替 | 地銀（銀行本体上場）をカバーできず、連結優先の設計思想とも不整合。**非推奨** |

### 案A/Bに共通して必要な実装

1. `no-industry` から銀行業・保険業を削除（保険業のうち一般様式で提出する少数事業者はそのまま動く可能性があるが、大半は業法様式）
2. `bs_subject`/`pl_subject` への業法様式ラベル追加（資産の部合計・負債の部合計・純資産の部合計・経常収益・経常費用等）※科目照合は完全一致（§4.2）
3. `AnalysisResult`/`AnalyzeInteractor` の業種別モデル分岐（案Aは専用式、案Bは corporate_value の nullable 化）
4. valuation・corporate_view・ランキング/分布集計の null 耐性（corporate_value 前提の箇所の洗い出し）
5. IFRS様式（jpigp・流動性配列・「資本合計」「当期利益」ラベル）への対応（保険大手・一部銀行）
6. 過去分の取り込み: 除外業種の書類は `document` テーブルに登録済みだが未ダウンロード。対象化後に過去提出分のダウンロード・スクレイピングの再走が必要（スケジューラの遡及日数を超える期間は手動リカバリ）
7. 株価履歴: 対象化時点から取得開始となるため、過去平均・バリュエーションが安定するまで期間を要する
8. モデル・係数変更に該当するため、適用後は全期間一括再計算（`POST /v1/admin/analysis/recalculate`）の実行が必要（CLAUDE.md のモデル検証セマンティクスに従う）

## 7. 調査方法の記録

- 本番サーバの `decode` ツリーを主要行・大手保険6社のEDINETコード（ファイル名に埋め込まれる）で検索し、XBRL不存在を確認（§2の「ダウンロード前フィルタ」の実地裏付け）。
- 検証用XBRLはEDINETの書類閲覧サイト（キーレス）からブラウザ自動操作で本文htmを取得。`ix:` 属性・TextBlock `name` 属性が保持されていることを確認したうえでキーワード照合に使用。
- キーワード照合は2つの独立した抽出方法（p要素単位のテキスト抽出／全タグ除去テキスト）で二重に実施し、結果が一致することを確認済み。
- EDINETコードリストの業種集計も2手法（CSVパーサ／grep）で照合。手法間差異は「提出者種別」列と「提出者業種」列の取り違えが原因と特定し、提出者業種ベースの値（§3の表）に確定した。
