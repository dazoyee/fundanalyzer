# タスクノート: 評価連鎖の恒久停止・株式総数異常・鮮度可視化・UA遮断ホットフィックスの一括対応

対象リリース: v2.5.4 / v2.5.5 / v2.5.6

## 背景

複数の独立した経路で「評価・ランキングが実態と乖離した状態のまま自動更新されない」という
データ品質問題が確認された。個社の評価停止（探索窓切れ）、株式総数の桁誤り（単位注記の
読み違い）、上場廃止・長期停滞銘柄がランキングに残り続ける問題、外部サイトのUser-Agent
遮断による株価取得停止が同時期に顕在化したため、一連の対応を本ノートにまとめて記録する。

## 経緯・原因・対応

### 1. 評価連鎖の恒久停止（v2.5.4）

**経緯・原因**: 月次評価（`ValuationSpecification`）は対象日の前後±5日の株価を探索して
評価基準日を確定する方式だった。株価取得が何らかの理由で一時的に途切れると、探索窓に
該当する株価が存在せず評価が失敗し、失敗した月を起点に翌月以降の探索基準日もずれ続けるため、
一度停止すると自然回復しない恒久停止に陥る。本番調査で512社がこの状態で滞留していることを確認した。

**対応**:
- 評価基準日の決定方式を、固定探索窓（±5日）から**前方スナップ**（対象日以降で最初に存在する
  株価日を採用、上限日数を設定値化）に変更。上限は `app.config.valuation.forward-snap-limit-days`
  （既定45日）。
- 滞留分を解消するための **catch-up** 処理を新設。件数確認用の
  `GET /v1/admin/valuation/catch-up/preview` と実行用の `POST /v1/admin/valuation/catch-up` を
  手動エンドポイントとして追加し、日次スケジューラにも組み込んで以後は自動的に前方スナップの
  取りこぼしが解消されるようにした（`app.config.valuation.catch-up-max-iterations` で1回あたりの
  反復上限を制御）。
- `POST /v1/admin/analysis/recalculate` を、係数変更時の全件再計算に加えて **グレアム指数が
  null の行の再計算**にも対応するよう拡張した。
- `StockScheduler#insert` を個社の例外で全体が止まらないよう継続化し、`notifyStaleSources` を
  `finally` 化して通知処理の例外が後続処理をブロックしないようにした。

**検証結果**: 滞留していた512社を解消。例として証券コード9278（ブックオフグループホールディングス）は
2025-10-15を最後に評価が止まっていたが、前方スナップとcatch-up適用後は2026-05-15まで月次評価が
自動的に再開されていることを確認した。

### 2. 株式総数抽出・ランキング鮮度・株価停滞の可視化（v2.5.5）

**経緯・原因**: 株式総数のスクレイピングがテーブル境界を越えて隣接値を拾う場合があり、また
「千株」等の単位注記がある場合に単位換算をせず生値をそのまま保存していたため、実際の株式総数と
大きく乖離した値が算出に使われる余地があった。加えて、上場廃止銘柄や長期間評価が更新されていない
銘柄がランキングに残り続け、利用者が鮮度を判別できない状態だった。

**対応**:
- 株式総数抽出のテーブル境界保持を修正し、「千株」等の単位注記がある場合は自動換算せず
  **エラー化**して処理対象外とするようにした（`number-of-shares-lower-limit=10000` の下限
  サニティチェックも追加し、明らかに桁が足りない値を弾く）。
- ランキングから**上場廃止銘柄**と**対象日から90日超経過した銘柄**（`ranking-exclude-days=90`）を
  除外し、45日超経過した銘柄には鮮度バッジ（`ranking-stale-badge-days=45`）を表示するようにした。
- 銘柄単位の株価取得停滞を検知する画面バナー（`company-staleness-alert-days=14`）を追加した。
  通知手段はSlackではなく画面表示のみとした。

**検証結果**: ランキング表示・鮮度バッジ・停滞バナーが設計どおりに機能することを確認（詳細は後述の
ホットフィックスでのN+1解消と合わせて検証）。

### 3. minkabu/nikkei User-Agent遮断ホットフィックス（v2.5.6）

**経緯・原因**: minkabu・nikkei の両サイトがUser-Agentによるアクセス制限を導入し、Javaの
デフォルトUser-Agentでのリクエストが403で拒否されるようになった（本番環境でフルブラウザ相当の
User-Agentを使うと200が返ることを実証済み）。minkabuへのアクセスがサーキットブレーカーをOPENに
遷移させ、上場確認（isLived判定）が全滅したことで株価取込みそのものが停止し、株価停滞（stale）
銘柄が2979件に達した。

**対応**:
- jsoup用の `RestTemplate` に設定可能なUser-Agentを追加した（`app.config.rest-client.jsoup.user-agent`）。
  設定値はフルブラウザ相当の文字列とし、以後の遮断発生時も設定変更のみで追従できるようにした。
- 併せて、staleness バナー判定のN+1クエリを `GROUP BY` による一括集計に変更し、
  `/v3/analysis` の応答時間を33秒から6.3秒に短縮した。

**検証結果**: User-Agent設定変更後、minkabu・nikkeiへのアクセスが200で成功することを確認し、
stale銘柄の株価取込みが再開した。

### 4. 株式総数の桁誤りデータ是正（9278・8925）

**経緯・原因**: 証券コード9278（ブックオフグループホールディングス）は、有価証券報告書が
発行済株式数を「千株」単位で表記していたにもかかわらず、その注記が反映されずスクレイピング時に
1000分の1の値（20,547）で保存されていた（2019〜2025年の21行）。この桁誤りにより理論株価が
実態の1000倍近くに算出され、ランキングの割安度が186741%という異常値で表示されていた。

**対応**:
- EDINET原本のXBRLを直接突合し、正しい株式総数（20,547,000株）を確定した。
- 該当21行を対象に `financial_statement` の株式総数を ×1000 でDB UPDATEし、その後
  `POST /v1/admin/analysis/recalculate` により再計算した
  （`updated=110,138` 件・`valuationUpdated=167,483` 件）。
- 証券コード8925（アルデプロ）についても株式総数の疑義を確認したが、`company.removed='1'`
  （上場廃止・対象外）であることを確認し、是正対象外と判断した。

**検証結果**: 再計算後、9278のランキング表示の割安度異常（186741%）が解消され、圏外（対象外表示）
になることを確認した。

## 設計判断（恒久的なWHY）

| 判断 | 理由 |
|---|---|
| 評価基準日は前方スナップ・上限日数を設定値化 | 固定探索窓（±5日）は株価取得の一時的な欠落に対して脆弱で、失敗が翌期以降に連鎖する。前方スナップは「対象日以降で最初に存在する株価」を機械的に採用するため連鎖しない。上限を設けるのは、株価取得が長期間途絶えた銘柄まで無制限に将来の株価で評価してしまうことを防ぐため |
| catch-upは手動プレビュー＋実行に加えて日次スケジューラにも組み込む | 手動実行のみでは再発時に人手を要し、スケジューラ組み込みのみでは初回の大量滞留解消時に件数・影響を事前確認できない。両者を併設することで初回は確認しながら実行し、以後は自動で追従する |
| グレアム指数のnull再計算は既存の `recalculate` エンドポイントに集約する | 係数変更時の全件再計算と欠損値の再計算は「保存済みの評価値をモデル定義に基づいて作り直す」という同じ操作であり、別エンドポイントに分けると経路が増えるだけで利用者・運用側の判断コストが上がる |
| 単位注記（千株等）はエラー化し自動補正しない | 単位注記の書式は提出者ごとに揺れがあり、自動換算のロジックを増やすほど誤換算のリスクが積み上がる。エラー化して処理対象外にすれば、少なくとも誤った値が保存されることはなく、個別確認で安全に是正できる |
| ランキングは除外90日・バッジ45日の2段階 | 除外は「もはや現在の実態を表さない可能性が高い」銘柄を一覧から取り除くための閾値、バッジは「まだ一覧には残すが鮮度に注意が必要」という中間状態を示すための閾値であり、両者は目的が異なるため別の閾値として管理する |
| 株価停滞の通知は画面表示のみ（Slack通知はしない） | Slack通知は個別銘柄の停滞のような高頻度・大量発生しうる事象の通知先としては運用負荷が高い。画面上で気づいたときに確認できれば十分という判断のもと、通知チャネルを増やさない |
| jsoup用RestTemplateのUser-Agentを設定値化 | 外部サイトのアクセス制限方式（User-Agent判定）は今後も変わりうるが、変わるたびにコード変更・再デプロイを要する構成は復旧までの時間がかかる。設定値化しておけば、設定変更のみで追従できる |
| 株式総数の桁誤りはDB直接UPDATE＋recalculateで是正し、遡及的なスクレイピングロジック変更はしない | 個社固有の表記揺れ（今回は「千株」注記の見落とし）は汎用ロジックで全件を再検証するより、実際に異常が確認された対象のみをEDINET原本と突合して是正する方が確実で、既存の正常データに副作用を与えない |

  `app.config.scraping.number-of-shares-lower-limit` /
  `app.config.valuation-ranking.ranking-exclude-days` /
  `app.config.valuation-ranking.ranking-stale-badge-days` /
  `app.config.stock.company-staleness-alert-days` /

  `POST /v1/admin/analysis/recalculate` の拡張

- `domain/value/ValuationCatchUpPreview.java` / `ValuationCatchUpResult.java`

## スコープ外（別途対応）

- Slack通知の廃止方針そのもの（今回は株価停滞バナーを画面表示のみとした個別判断であり、
  他の通知系統の扱いは対象外）
- IFRS提出者など、株式総数抽出以外の科目照合の揺れ（別課題として扱う）
