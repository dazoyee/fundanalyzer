# セキュリティ方針テンプレート

セキュリティ対策を「とりあえず実装する」のではなく、**観点ごとに採用／不採用を文書化** することで、漏れを防ぎ、半年後の再議論を防ぐ。

> **使い方**: プロジェクト初期セットアップ時、または [workflow.md](workflow.md) の「ステップ 3：影響設計」で本テンプレートをコピーして埋める。**採用しない観点についても、見送り理由を文書化する**（暗黙の見送り禁止）。

---

## セキュリティ観点（一覧）

| 観点 | 主な対象 | 主な脅威 |
|---|---|---|
| **認証** | ログイン・セッション・API トークン | 成りすまし・セッション乗っ取り |
| **認可** | 権限管理・アクセス制御 | 権限昇格・横断アクセス |
| **入力検証** | リクエスト・フォーム・ファイルアップロード | 各種注入攻撃・スクリプト実行 |
| **機密情報管理** | シークレット・個人情報 | 漏洩・不正利用 |
| **監査ログ** | 重要操作・ログイン履歴・データ変更 | 否認・不正検知失敗 |
| **暗号化** | 保存時・通信時 | 盗聴・データ漏洩 |
| **エラー処理** | 例外・エラーメッセージ | 内部情報漏洩 |
| **依存ライブラリ** | サードパーティ依存 | 既知脆弱性の混入 |

---

## 戦略決定テンプレート

```markdown
# セキュリティ方針 — <プロダクト名>

## 1. プロダクト前提
- 取扱データ: 例) 個人情報あり / 決済情報あり / 公開情報のみ
- 想定脅威: 例) 外部攻撃 / 内部不正 / 誤操作
- コンプライアンス要件: 例) 個人情報保護法 / 業界基準
- リリース対象: 例) 社内利用 / 限定公開 / 一般公開

## 2. 観点ごとの方針

### 2.1 認証
- **採用**: <例: パスワード + 多要素認証 / シングルサインオン連携>
- **採用しない**: <例: ソーシャルログイン>
- **理由**: <例: 取扱データが業務情報のため、外部 ID プロバイダ連携を避ける>

### 2.2 認可
- **採用**: <例: ロールベースアクセス制御（RBAC）/ リソース単位の権限チェック>
- **採用しない**: <例: 属性ベースアクセス制御（ABAC）>
- **理由**: <例: 役割が明確で、属性ベース制御は過剰>

### 2.3 入力検証
- **採用**: <例: Bean Validation 等のフレームワーク標準検証 / コントローラ層での @Valid 強制>
- **採用しない**: <例: 独自検証ライブラリ>
- **理由**: <例: 標準で十分かつ保守性が高い>

### 2.4 機密情報管理
- **採用**: <例: 環境変数 / 機密情報管理サービス（Vault 等）>
- **採用しない**: <例: 設定ファイルへの直書き>
- **理由**: <例: シークレットを Git に含めない原則>

### 2.5 監査ログ
- **採用**: <例: ログイン・権限変更・重要データ変更を記録 / 改ざん防止>
- **採用しない**: <例: 全 API 呼び出しのログ>
- **理由**: <例: ストレージコストとプライバシー観点>

### 2.6 暗号化
- **採用**: <例: 通信時 TLS 1.3 / 保存時 DB 暗号化>
- **採用しない**: <例: アプリ層での独自暗号化>
- **理由**: <例: 標準機構で十分>

### 2.7 エラー処理
- **採用**: <例: スタックトレースをレスポンスに含めない / 詳細はサーバログのみ>
- **採用しない**: なし
- **理由**: 情報漏洩防止の基本

### 2.8 依存ライブラリ
- **採用**: <例: 脆弱性スキャンの定期実行 / 更新ポリシーの明文化>
- **採用しない**: <例: 全依存の最新追従>
- **理由**: <例: 安定性とのトレードオフを考慮>

## 3. 段階定義（初期段階／本格運用）

| 観点 | 初期段階 | 本格運用 |
|---|---|---|
| 認証 | パスワードのみ | + 多要素認証 |
| 入力検証 | 主要エンドポイントのみ | 全エンドポイント |
| 監査ログ | ログイン・重要操作 | + データ変更履歴 |
| 暗号化 | 通信時 TLS のみ | + 保存時暗号化 |
| 依存ライブラリ | 手動チェック | + 自動スキャン |

## 4. レビュー周期
- 半年に 1 回、または重要なリリース前にレビュー
- 観点ごとに「採用しない理由」が現状に合っているか確認

## 5. 採用しなかった理由の検証
- 半年後・1 年後のレビュー時期: <YYYY-MM>
- 見直しトリガー: <例: 取扱データ種別の変更時 / 利用者数の節目>
```

## 記入時の注意

### 「採用しない理由」を必ず書く

「やらない」と決めることは「やる」と決めることと同じく重要。理由を残さないと、半年後に「なぜこの観点を採用していないのか」を再議論することになる。

### 段階定義で過剰実装を避ける

最初から本気のセキュリティを全部やる必要はない。**初期段階で必須／本格運用で追加** を分けて記述する。ただし、機密情報管理・通信暗号化・基本的な入力検証は初期段階から必須。

### 採用判定の問い（参考）

| 観点 | 採用判定の問い |
|---|---|
| 認証 | 利用者を特定する必要があるか |
| 認可 | 権限による画面・データの出し分けがあるか |
| 入力検証 | 利用者入力をデータストア・外部システム・画面に反映するか |
| 機密情報管理 | シークレット・個人情報・決済情報を扱うか |
| 監査ログ | 操作の追跡・否認防止が必要か |
| 暗号化 | データ漏洩時の影響度はどの程度か |
| エラー処理 | エラーメッセージから内部構造が推測されないか |
| 依存ライブラリ | サードパーティ依存にどの程度依存しているか |

## 一般的な脆弱性観点（参考）

入力検証・認証認可で防ぐ代表的な脆弱性。プロジェクト固有規約・スキャンツールで対応する。

| 脆弱性 | 概要 | 対策 |
|---|---|---|
| 注入攻撃 | データストアやコマンドへの不正な値の注入 | パラメータ化クエリ・エスケープ |
| スクリプト実行 | 画面に不正スクリプトを埋め込まれる | 出力時エスケープ・コンテンツセキュリティポリシー |
| 偽造リクエスト | 利用者を装って不正リクエストを送られる | トークン検証・参照元確認 |
| 認証不備 | パスワード強度不足・セッション管理の弱さ | 強度ポリシー・セッション無効化機構 |
| 認可不備 | 権限のないリソースへのアクセスを許容してしまう | リソース単位の権限チェック |
| 機密情報露出 | エラー画面・ログ・レスポンスから内部情報漏洩 | 例外ラップ・ログ出力フィルタ |
| 安全でない直接参照 | 識別子の推測でリソースに直接アクセスされる | 参照可能性チェック・推測困難な識別子 |
| 設定ミス | 公開すべきでないエンドポイント・機能の露出 | 本番設定の最小公開原則 |

## ドキュメント構造の規約（参考）

具体的な実装規約・コーディングスタイルは **各プロジェクトの規約** に従う。本ガイドラインは **どの観点を採用するか** の決定までを扱い、**どう実装するか** はプロジェクト規約（採用言語・フレームワーク・スキャンツール）に委ねる。

各プロジェクトで規約として整備しておくとよい項目：
- シークレット管理の具体的手段（環境変数 / 機密情報管理サービス）
- ログ出力規約（出力レベル・PII（個人識別情報）マスキング）
- 認証・認可の実装パターン
- 依存ライブラリ更新ポリシー（脆弱性発見時の対応 SLA）
