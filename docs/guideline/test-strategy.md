# テスト戦略テンプレート（品質特性モデル参照）

テストを「とりあえず書く」のではなく、**ソフトウェア品質特性の標準モデル（ISO/IEC 25010 等の品質特性モデル）の観点** から必要なテストを導出する。

> **使い方**:
> - **プロジェクト初期セットアップ時** に、本テンプレートの「戦略決定テンプレート」セクションをコピーして初版を作成する
> - **以降のタスク** では、[workflow.md](workflow.md) の「ステップ 3.4：品質設計の確認・更新」で初版を確認し、必要があれば差分更新する（毎タスクで丸ごと再作成しない）
> - **採用しないテスト種別についても、見送り理由を文書化する**（暗黙の見送り禁止）
> - 本テンプレートは汎用ガイド。**プロジェクト固有のテスト規約（命名・アサーション等）はプロジェクト規約が優先する**（プロジェクト固有規約がある場合はそちらを参照する。本リポジトリでは技術規約集側の [`../tech-guideline/04-test/`](../tech-guideline/04-test/README.md) が確定規約に相当する）

---

## テスト品質特性（観点一覧）

| 主特性 | 副特性（抜粋） | 説明 |
|---|---|---|
| **機能適合性** | 完全性／正確性／適切性 | 必要な機能が、要求された結果を返すか |
| **性能効率性** | 時間効率／資源効率／容量 | 応答時間・スループット・リソース消費 |
| **互換性** | 共存性／相互運用性 | 他システム・他バージョンと共存できるか |
| **使用性** | 学習容易性／操作性／アクセシビリティ | 利用者が使えるか |
| **信頼性** | 成熟性／可用性／障害許容性／回復性 | 落ちないか・落ちても復旧できるか |
| **セキュリティ** | 機密性／完全性／否認防止／真正性 | 守れているか |
| **保守性** | モジュール性／再利用性／解析性／修正性／試験性 | 後で直せるか |
| **移植性** | 適応性／設置性／置換性 | 別環境で動くか |

## 戦略決定テンプレート

> **↓ ここから下をテンプレートとしてコピー ↓**

```markdown
# テスト戦略 — <プロダクト名>

## 1. プロダクト前提

| 項目 | 記述形式 | 例 |
|---|---|---|
| ターゲット利用者数 | 数値（または範囲）| 100 / 10,000 / 100 万以上 |
| データ量 | レコード数（最大規模）| 1 万件 / 1 億件 |
| 可用性要求 | 数値またはカテゴリ | ベストエフォート / 99.9% / 99.99% |
| 重要データ | カテゴリ | 個人情報あり / 決済情報あり / 公開情報のみ |
| リリース頻度 | 頻度 | 月 1 / 週 1 / 日次 |

## 2. テスト種別の定義

採用するテスト種別ごとに **対象範囲・依存の扱い** を明示する。「結合テスト」と一括りにせず、**どこまでをモックして何を実体で動かすか** を揃えることで、設計のブレと「思っていたテストと違う」を防ぐ。

### 2.1 採用するテスト種別

| テスト種別 | 対象範囲 | 依存の扱い | ツール例 |
|---|---|---|---|
| 単体テスト | 単一クラス／関数の振る舞い | 依存はすべてモック | JUnit + Mockito |
| 結合テスト | 複数クラス連携（DI コンテナ起動） | 内部はモックせず、外部 I/O のみモック | `@SpringBootTest` |
| Dao 統合テスト | リポジトリ層 + 実 DB | DB は Testcontainers／組込 DB（モックしない） | Doma + Testcontainers |
| API テスト | HTTP 境界（Controller 入口）からサービス層 | サービス層は実体／外部 API はモック<br>※ プロジェクトによってはサービス層もモックする方針もあり得る | MockMvc |
| 起動テスト | フレームワーク起動 + Bean 解決 + 設定読込 | 外部 I/O はモック／プロファイル: test | `@SpringBootTest`（空テスト）／`ApplicationContextRunner` |
| スモーク E2E | デプロイ／起動後に Happy Path を 1 本通す | 実環境起動（外部はスタブ可）| `mvn spring-boot:run` + ヘルスチェック + 主要 1 シナリオ |
| E2E テスト | ブラウザ操作起点で全層 | 原則すべて実体／外部のみスタブ可 | Playwright 等 |
| 性能テスト | 主要 API・バッチの応答時間／スループット | 実環境相当（ステージング DB／同時接続シミュレート）| Gatling / JMeter |
| セキュリティテスト | 静的解析・脆弱性スキャン・侵入試験 | 静的解析は実コード／侵入試験は実環境 | SpotBugs / OWASP Dependency-Check / 外部委託 |

> 上記はサンプル。プロジェクトの技術スタックに合わせて行を追加・削除し、ツール名を確定させる。

### 2.2 検討候補（採否を必ず判定する）

以下は採否を一度は議論する候補。**採用するなら §2.1、不採用なら §2.3** に振り分ける（暗黙の見送り禁止）。

- 契約テスト（Pact 等、サービス間整合）
- ミューテーションテスト（PIT 等、テストの強度測定）
- ビジュアルリグレッション（フロントエンド画面の意図しない変化検出）
- カオス試験（障害注入で信頼性を検証）

### 2.3 採用しないテスト種別と見送り理由

| 種別 | 見送り理由 | 再検討トリガー |
|---|---|---|
| <例: ミューテーションテスト> | <例: テストカバレッジ目標未達のため、まず基本テストの拡充を優先> | <例: カバレッジ 80% 達成後> |
| <例: 侵入試験（ペネトレーションテスト）> | <例: 本リリース前に外部委託で実施予定> | <例: 本リリース 1 か月前> |

## 3. 品質特性ごとのテスト方針

### 3.0 品質特性 × テスト種別 マトリクス

各品質特性を「どのテスト種別で担保するか」を一覧で示す。

> **凡例**
> - **◎**: 主担当（その品質特性の中心となるテスト種別）
> - **○**: 補助（主担当を補う位置づけ）
> - **△**: 部分的にカバー
> - **空欄**: 対象外（採用しないことの明示。「未記入」ではない）

| 品質特性 | 単体 | 結合 | Dao 統合 | API | 起動 | スモーク | E2E | 性能 | セキュリティ |
|---|---|---|---|---|---|---|---|---|---|
| 機能適合性 | ◎ | ○ | ○ | ◎ | ○ | ○ | △ |   |   |
| 性能効率性 |   | △ |   | △ |   |   | △ | ◎ |   |
| 互換性 |   |   |   |   |   |   | ◎ |   |   |
| 使用性 |   |   |   |   |   | △ | ◎ |   |   |
| 信頼性 | ○ | ◎ |   | ○ | ◎ | ◎ | △ |   |   |
| セキュリティ | ○ | ○ |   | ○ |   |   |   |   | ◎ |
| 保守性 | ◎ | ○ |   |   |   |   |   |   |   |
| 移植性 |   | ○ |   |   | ◎ | ○ | ○ |   |   |

> **マトリクス運用ルール**
> 1. **§3.0 マトリクスは採用したものだけ書く**（◎・○・△）。採用しないテスト種別は §2.3 で見送り理由を残し、マトリクスでは空欄にする
> 2. §3.1 以降では「◎・○ をどう具体化するか」を **観点・テストケース粒度** で記述する（種別の説明はマトリクスに任せる）
> 3. 「保守性」は単体／結合テストの存在自体（リファクタ耐性）が主担当。**カバレッジ計測・複雑度規定** は §4 で別途扱う
> 4. 「使用性」「移植性」「信頼性 (の障害注入)」など、上記 7 種別では担保しきれない観点は **手動 UAT・カオス試験・コンテナ動作確認** など補助活動で補う。採用するなら §2.1 に行を追加し、§2.3 で不採用も明示する

### 3.1 機能適合性
- **観点**: <例: 入力境界値／業務ルール網羅／異常系応答コード>
- **採用**: <例: 単体テスト（Service の業務ロジック）／結合テスト（複数 Service 連携）／API テスト（Controller 経由）>
- **採用しない**: なし
- **理由**: コア機能の正確性は最優先

### 3.2 性能効率性
- **観点**: <例: 主要 API のレスポンスタイム p95／同時 100 接続でのスループット>
- **採用**: <例: 主要 API の応答時間計測・想定同時接続数での挙動確認>
- **採用しない**: <例: 想定の 10 倍を超える負荷試験>
- **理由**: <例: 想定利用者数のため過剰>

### 3.3 互換性
- **観点**: <例: 主要ブラウザでの表示・動作>
- **採用**: <例: E2E テスト（Chrome / Edge）>
- **採用しない**: <例: 旧世代ブラウザ対応>
- **理由**: <例: 社内利用のため最新ブラウザのみで十分>

### 3.4 使用性
- **観点**: <例: 主要画面の操作完了までの導線>
- **採用**: <例: モックでの実機操作確認（手動 UAT）>
- **採用しない**: <例: アクセシビリティ自動テスト>
- **理由**: <例: 初期段階では手動確認で十分>

### 3.5 信頼性
- **観点**: <例: DB 接続失敗時のフォールバック・リトライ動作>
- **採用**: <例: 異常系の結合テスト・リトライ動作の単体検証>
- **採用しない**: <例: 障害注入試験（カオスエンジニアリング）。詳細は §2.3 を参照>
- **理由**: <例: 後続フェーズで導入予定>

### 3.6 セキュリティ
- **観点**: <例: 入力検証／認証認可／SQL インジェクション・XSS 対策>
- **採用**: <例: 入力検証単体／認証認可結合／静的解析>
- **採用しない**: <例: 侵入試験（ペネトレーションテスト）。詳細は §2.3 を参照>
- **理由**: <例: 本リリース前に外部委託で実施>

### 3.7 保守性
- **観点**: <例: テストカバレッジ・複雑度上限・既存テスト未変更>
- **採用**: <例: 単体テスト存在の必須化／カバレッジ目標 §4 に従う／複雑度上限の規定>
- **採用しない**: なし
- **理由**: 長期保守の前提

### 3.8 移植性
- **観点**: <例: コンテナ環境での起動・本番相当環境での動作>
- **採用**: <例: コンテナ動作確認（リリース前）>
- **採用しない**: <例: 複数 OS 対応テスト>
- **理由**: <例: 本番環境が単一のため>

## 4. カバレッジ目標

カバレッジは **測定対象に何を含めるか** を明確にして算出する。除外を明文化しないと、Record や Config を含めるか否かで見かけの数値がブレ、目標値の意味が失われる。

### 4.1 対象区分

| 区分 | 該当カテゴリ | 判定基準（コード性質）| 運用判定（どのテストでカバーするか）|
|---|---|---|---|
| **対象**（目標 <例: 80%>）| Service の業務メソッド／Controller のハンドラ／カスタム Validator／ドメインロジックを含む Utility／ロジックを持つ enum メソッド／ロジックを持つ Filter・Interceptor・AOP アスペクト | 条件分岐・状態遷移を持つ振る舞いコード | 単体／結合／API テスト |
| **部分対象** | Doma Dao（カスタムクエリ）／カスタムリポジトリ／`@Scheduled` バッチジョブ（ロジック含む場合）| クエリ／スケジュール起動部 | Dao 統合テスト／結合テスト |
| **除外** | Record／DTO／POJO／`@Configuration`／`@SpringBootApplication`／例外クラス（ロジックを持たないもの）／自動生成 Mapper／getter のみのクラス／getter のみの enum | 振る舞いを持たない／フレームワーク責務 | （計測対象外）|

> **エッジケース判定**
> - **ロジックを持つ Record**: 「対象」（コンパクトコンストラクタや独自メソッドに条件分岐がある場合）
> - **enum メソッド**: ロジックを含むなら「対象」、列挙値・getter のみなら「除外」
> - **`@Scheduled` バッチジョブ**: 業務処理を含むなら「部分対象」、薄い委譲のみなら「除外」
> - **Filter / Interceptor / AOP アスペクト**: 業務ロジックが入るなら「対象」、ヘッダ操作・ログ出力のみなら「除外」

### 4.2 全体目標
- 「対象」モジュール: <例: 80%>
- 全体（除外を差し引いた母集団）: <例: 70%>

> **プロジェクト規約との関係**: JaCoCo の strict ルール等で機械強制するのは「対象」モジュールの目標値。「全体」値は参考指標として扱う（プロジェクト規約のカバレッジ閾値は本目標と整合させる）。

## 5. テスト実行タイミング

§2.1 で採用したテスト種別はすべて、いずれかのタイミングで実行する。タイミング表は §2.1 と種別が 1:1 対応するよう確認する。

| タイミング | 実行するテスト |
|---|---|
| ローカルコミット前 | 単体テスト / 静的解析 / 起動テスト |
| ローカル実装完了時（コミット前） | + スモーク E2E（実装エージェントによる Happy Path 1 本通し）|
| プルリクエスト作成時（CI） | 単体 / 結合 / Dao 統合 / API / 起動 / カバレッジ計測 |
| 主ブランチ取込時（採用ブランチ戦略に従う） | + 静的セキュリティ解析・脆弱性スキャン |
| リリース前 | + E2E / 性能テスト（主要 API の応答時間計測）|
| 定期（週次／月次など）| <例: 脆弱性スキャン定期実行>|
| リリース後（必要時）| <例: スモーク E2E 再実行>|
```

## 記入時の注意

### 「採用しない理由」を必ず書く

「やらない」と決めることは「やる」と決めることと同じく重要。理由を残さないと、半年後に「なぜこのテストがないのか」を再議論することになる。**§2.3 と §3.x の「採用しない／理由」は必ず埋める**。

### 採用済テストの強化計画は段階定義する（§6 とは別観点）

最初から本気のテストを全部やる必要はない。**初期段階で必須／本格運用で追加** を分けて記述する。本セクションは「採用済テストの強化スケジュール」を扱う。「不採用テストの再検討」は §6 で扱う（観点が異なる）。

| 観点 | 初期段階 | 本格運用 |
|---|---|---|
| 性能テスト | 軽い動作確認のみ | 想定負荷の 2 倍まで負荷試験 |
| セキュリティ | 静的解析のみ | + 侵入試験（ペネトレーションテスト） |
| 互換性 | 主要環境のみ | + サポート対象環境すべて |

### 採用判定の問い（参考）

| 副特性 | 採用判定の問い |
|---|---|
| 性能効率性 | 「同時利用 X 名で Y 秒以内に返す」要求があるか |
| 信頼性 | データストア接続失敗時に「エラー画面で諦める」で許容されるか |
| セキュリティ | 個人情報・決済情報・社外秘情報を扱うか |
| 保守性 | 半年以上運用する可能性があるか |
| 互換性 | 利用環境が固定か、不特定多数か |

## アサーション・テスト構造の規約（参考）

具体的なアサーション・テスト構造の規約は **各プロジェクトの規約が優先する**。本ガイドラインは **何のテストを書くか** の決定までを扱い、**どう書くか** はプロジェクト規約に委ねる。

各プロジェクトで規約として整備しておくとよい観点：
- アサーション（テストで「期待する結果」を検証する記述）に使うライブラリ（標準アサーションのみ／追加ライブラリ可）
- テスト構造（グループ化・命名規約）
- テスト記述言語（テスト名を日本語で書くか英語で書くか）
- パラメータ化テスト（同じテストを複数パターンの入力で繰り返す手法）の活用方針

> **プロジェクト規約の例**: 「JUnit 5 標準アサーションのみ／AssertJ 禁止／`@Nested` + `@DisplayName`（日本語）」のように、テストの書き方ルールはプロジェクト固有規約で確定させる。本リポジトリでは技術規約集側の [`../tech-guideline/04-test/`](../tech-guideline/04-test/README.md) を一次規約とする。
