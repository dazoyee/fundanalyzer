# テスト戦略テンプレート（品質特性モデル参照）

テストを「とりあえず書く」のではなく、**ソフトウェア品質特性の標準モデル（ISO/IEC 25010 等の品質特性モデル）の観点** から必要なテストを導出する。

> **使い方**: プロジェクト初期セットアップ時、または [workflow.md](workflow.md) の「ステップ 3：影響設計」で本テンプレートをコピーして埋める。**採用しないテスト種別についても、見送り理由を文書化する**（暗黙の見送り禁止）。

---

## テスト品質特性（観点一覧）

| 主特性 | 副特性（抜粋） | 説明 |
|---|---|---|
| **機能適合性** | 完全性／正確性／適切性 | 必要な機能が、要求された結果を返すか |
| **性能効率性** | 時間効率／資源効率／容量 | 応答時間・スループット・リソース消費 |
| **互換性** | 共存性／相互運用性 | 他システム・他バージョンと共存できるか |
| **使用性** | 学習容易性／操作性／アクセシビリティ | 利用者が使えるか |
| **信頼性** | 成熟性／可用性／障害許容性／回復性 | 落ちないか・落ちても復旧できるか |
| **セキュリティ** | 機密性／完全性／否認防止／真正性 | 守れているか |
| **保守性** | モジュール性／再利用性／解析性／修正性／試験性 | 後で直せるか |
| **移植性** | 適応性／設置性／置換性 | 別環境で動くか |

---

## 戦略決定テンプレート

```markdown
# テスト戦略 — <プロダクト名>

## 1. プロダクト前提
- ターゲット利用者数: 例) 100 / 10,000 / 100 万以上
- データ量: 例) 1 万件 / 1 億件
- 可用性要求: 例) ベストエフォート / 99.9% / 99.99%
- 重要データ: 例) 個人情報あり / 決済情報あり / 公開情報のみ
- リリース頻度: 例) 月 1 / 週 1 / 日次

## 2. 品質特性ごとのテスト方針

### 2.1 機能適合性
- **採用**: 単体テスト / 結合テスト / API テスト
- **採用しない**: なし
- **理由**: コア機能の正確性は最優先

### 2.2 性能効率性
- **採用**: <例: 主要 API の応答時間計測・想定同時接続数での挙動確認>
- **採用しない**: <例: 想定の 10 倍を超える負荷試験>
- **理由**: <例: 想定利用者数のため過剰>

### 2.3 互換性
- **採用**: <例: 主要ブラウザ動作確認>
- **採用しない**: <例: 旧世代ブラウザ対応>
- **理由**: <例: 社内利用のため最新ブラウザのみで十分>

### 2.4 使用性
- **採用**: <例: モックでの実機操作確認>
- **採用しない**: <例: アクセシビリティ自動テスト>
- **理由**: <例: 初期段階では手動確認で十分>

### 2.5 信頼性
- **採用**: <例: 異常系結合テスト・リトライ動作>
- **採用しない**: <例: 障害注入試験（カオスエンジニアリング）>
- **理由**: <例: 後続フェーズで導入予定>

### 2.6 セキュリティ
- **採用**: <例: 入力検証単体／認証認可結合／静的解析>
- **採用しない**: <例: 侵入試験（ペネトレーションテスト）>
- **理由**: <例: 本リリース前に外部委託で実施>

### 2.7 保守性
- **採用**: <例: テストカバレッジ X%・複雑度上限の規定>
- **採用しない**: なし
- **理由**: 長期保守の前提

### 2.8 移植性
- **採用**: <例: コンテナ環境での動作確認>
- **採用しない**: <例: 複数 OS 対応テスト>
- **理由**: <例: 本番環境が単一のため>

## 3. カバレッジ目標
- ビジネスロジックを含むモジュール: <例: 80%>
- 値オブジェクト・設定クラス・自動生成コード: 対象外
- 全体: <例: 70%>

## 4. テスト実行タイミング
| タイミング | 実行するテスト |
|---|---|
| ローカルコミット前 | 単体テスト / 静的解析 |
| プルリクエスト作成時（CI） | 単体テスト / 結合テスト / カバレッジ |
| マージ時 | + 静的セキュリティ解析 |
| リリース前 | + 主要 API の応答時間計測 |

## 5. 採用しなかった理由の検証
- 半年後・1 年後のレビュー時期: <YYYY-MM>
- 見直しトリガー: <例: 利用者数の節目に達した時点>
```

## 記入時の注意

### 「採用しない理由」を必ず書く

「やらない」と決めることは「やる」と決めることと同じく重要。理由を残さないと、半年後に「なぜこのテストがないのか」を再議論することになる。

### 初期段階／本格運用で段階定義する

最初から本気のテストを全部やる必要はない。**初期段階で必須／本格運用で追加** を分けて記述する。

| 観点 | 初期段階 | 本格運用 |
|---|---|---|
| 性能テスト | 軽い動作確認のみ | 想定負荷の 2 倍まで負荷試験 |
| セキュリティ | 静的解析のみ | + 侵入試験（ペネトレーションテスト） |
| 互換性 | 主要環境のみ | + サポート対象環境すべて |

### 採用判定の問い（参考）

| 副特性 | 採用判定の問い |
|---|---|
| 性能効率性 | 「同時利用 X 名で Y 秒以内に返す」要求があるか |
| 信頼性 | データストア接続失敗時に「エラー画面で諦める」で許容されるか |
| セキュリティ | 個人情報・決済情報・社外秘情報を扱うか |
| 保守性 | 半年以上運用する可能性があるか |
| 互換性 | 利用環境が固定か、不特定多数か |

## アサーション・テスト構造の規約（参考）

具体的なアサーション・テスト構造の規約は **各プロジェクトの規約** に従う。本ガイドラインは **何のテストを書くか** の決定までを扱い、**どう書くか** はプロジェクト規約（採用言語・フレームワーク・テストランナー）に委ねる。

各プロジェクトで規約として整備しておくとよい観点：
- アサーション（テストで「期待する結果」を検証する記述）に使うライブラリ（標準アサーションのみ／追加ライブラリ可）
- テスト構造（グループ化・命名規約）
- テスト記述言語（テスト名を日本語で書くか英語で書くか）
- パラメータ化テスト（同じテストを複数パターンの入力で繰り返す手法）の活用方針
