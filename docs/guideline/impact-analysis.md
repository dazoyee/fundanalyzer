# 影響範囲分析の運用手順（参照層・状態層・データ層）

既存プロダクトへの改修時、影響範囲を **機械的に** 洗い出すための分析手順。

> **使い方**: [workflow.md](workflow.md) の「ステップ 3：影響設計」で、タスクごとに本手順を実施する。結果は分析記録置き場に残す（配置例：`<docs>/research/<トピック>-impact.md`）。

---

## 3 つの分析層

| 層 | 分析対象 | 主な見落としリスク |
|---|---|---|
| **参照層** | 型・関数・定数の使用箇所 | 実行時の破損・コンパイルエラー |
| **状態層** | ステートマシン・ライフサイクル | データ破損・矛盾遷移 |
| **データ層** | 既存データ・移行戦略 | 本番不整合・移行失敗 |

---

## 変更属性チェック（最初に必ず実施）

タスクごとに、以下 3 つの **変更属性** をチェックし、該当した属性に対応する層は詳細分析を実施する。
該当しない層は「該当なし（理由 1 行）」をタスク 1 md の `## Gate 1` セクションに必ず記載する（省略不可、抜け漏れ防止のため）。
1 層でも判断を飛ばすと典型的な事故が起きる。

| 変更属性 | 該当時に必須となる層 | 詳細分析の対象 |
|---------|------------------|--------------|
| シンボル参照（型・関数・定数・SQL カラム名 等）の変更/追加 | **参照層** | §参照層 の手順を実施 |
| 状態遷移・ライフサイクル（ステータス値・遷移ルール）の変更/追加 | **状態層** | §状態層 の手順を実施 |
| データの形（スキーマ・既存値の意味・関連テーブル）の変更 | **データ層** | §データ層 の手順を実施 |

3 属性すべてに該当しない場合は、本タスクは形式的な影響チェックのみで足りる
（例: 純粋なドキュメント整備、調査タスク、設定値の軽微な変更等）。
この場合も Gate 1 への「3 属性すべて該当なし」の明示記載は必須。

### 「該当なし」記載の例

```markdown
## Gate 1 影響範囲分析

- 参照層: 該当（変更属性: シンボル参照あり）→ 詳細分析を §参照層分析結果 に記載
- 状態層: 該当なし（状態遷移を変更しないため）
- データ層: 該当なし（スキーマ・データを変更しないため）
```

## 参照層：シンボル参照分析

**目的**: 改修対象のコードが **どこから使われているか** を網羅する。

### 手順

1. 改修対象のシンボル（関数・クラス・型・定数などの識別子）を特定する
2. プロジェクト全体で **参照箇所を機械的に抽出** する
   - 統合開発環境の参照検索
   - 全文検索ツール
   - 静的解析ツール
3. 抽出結果を一覧化（ファイル：行番号：コンテキスト）
4. 各参照箇所が改修によって **影響を受けるか／受けないか** 判定

### チェックリスト

- [ ] 関数の呼び出し元をすべて列挙したか
- [ ] 型の使用箇所（変数宣言・引数・戻り値・ジェネリクス）を列挙したか
- [ ] 定数の参照箇所（分岐文・条件式・連想配列のキー等）を列挙したか
- [ ] リフレクション・動的呼び出しの有無を確認したか
- [ ] 設定ファイル（YAML / JSON 等）からの参照がないか確認したか
- [ ] テストコードからの参照を別カテゴリで整理したか

### 出力例

```markdown
## 参照層：ステータス列挙型の使用箇所

| ファイル | 行 | 参照種別 | 影響 |
|---|---|---|---|
| <domain>/OrderService.<ext> | 42 | 分岐文 | 影響あり：新ステータス分岐追加 |
| <domain>/OrderRepository.<ext> | 88 | クエリ条件 | 影響あり：抽出条件見直し |
| <test>/OrderControllerTest.<ext> | 120 | テストデータ | 影響なし |
| 設定ファイル（YAML / JSON 等） | (なし) | - | - |
```

## 状態層：状態遷移分析

**目的**: 状態遷移図・ステートマシンの **矛盾・抜け** を検出する。

### 手順

1. 既存の状態遷移図を開く（[document-plan.md](document-plan.md) で整備済み前提）
2. 改修によって追加・変更される状態を特定する
3. **状態遷移マトリクス** を埋める
   - 行：遷移元
   - 列：遷移先
   - セル：許可される遷移か／禁止か／遷移トリガー
4. 矛盾遷移・到達不能状態・離脱不能状態を検出する

### 状態遷移マトリクスの形式

| 遷移元 ＼ 遷移先 | A | B | C | D |
|---|---|---|---|---|
| A | - | 許可（操作 1） | 禁止 | 許可（操作 2） |
| B | 禁止 | - | 許可（操作 3） | 許可（操作 2） |
| C | 禁止 | 禁止 | - | 禁止 |
| D | 許可（操作 4） | 禁止 | 禁止 | - |

> 状態遷移図は許可される遷移しか描かないため禁止遷移が曖昧になりやすいが、マトリクスは全セルを埋めるルールで禁止遷移も明示する。

### Mermaid stateDiagram の併用（推奨）

状態遷移を扱うタスクでは、マトリクス（禁止遷移を含む全セル網羅）に加えて **Mermaid `stateDiagram`** で許可遷移を可視化することを推奨する。
両者を併用することで、許可遷移（図）と禁止遷移（マトリクス）の双方が明示され、レビュー時の理解負担が下がる。

Mermaid 図はタスク 1 md の `## Gate 1` セクションに直接埋め込むか、`<docs>/research/<トピック>-impact.md` に集約する。

### チェックリスト

- [ ] 全「遷移元 × 遷移先」のセルを埋めたか（空欄禁止）
- [ ] 到達不能な状態がないか（どの遷移元からも入れない状態）
- [ ] 離脱不能な状態がないか（どの遷移先にも出られない状態 ＝ 終了状態以外）
- [ ] 双方向遷移の整合性（A → B が可なら B → A は？）
- [ ] 並行状態（同時に複数状態を取る）の有無

### 状態追加・変更時に波及する領域

| 影響先 | 確認項目 |
|---|---|
| API 仕様 | 新状態を返すレスポンスの追加 |
| 画面表示 | 新状態時の UI 表示 |
| 通知・メール | 新状態への遷移時の通知要否 |
| バッチ処理 | 新状態を対象にするバッチがあるか |
| 権限制御 | 新状態時の操作権限 |

## データ層：既存データ整合性分析

**目的**: 既存データへの影響と **移行戦略** を確定する。

### 手順

1. 改修によって変わる「データの形」を列挙する
   - スキーマ変更（カラム追加・削除・型変更）
   - 値の意味変更（既存値の解釈が変わる）
   - 関連テーブルへの影響
2. 既存データに対して **どのような移行が必要か** 判定する
3. 移行戦略を決定する（次節）
4. 切り戻し戦略を決定する

### 移行戦略の選択肢

| 戦略 | 概要 | 適用条件 | 注意点 |
|---|---|---|---|
| **インプレース更新** | 既存データを直接書き換える | データ量が少ない・短時間で完了 | 実行中の整合性ロック |
| **段階的バックフィル** | 新カラム等を追加し、既存データを少しずつ後追い更新する | データ量が多い・サービス継続が必要 | 中間状態でのアプリ動作 |
| **二重書き込み** | 旧スキーマと新スキーマの両方に同時に書き込んでから切り替える | スキーマ大幅変更 | 二重書き込みのコスト |
| **ブルーグリーン切替** | 旧環境（青）と新環境（緑）を並行稼働させ、一斉に切り替える | 互換性のない変更 | 切替手順と切り戻し |
| **移行不要** | スキーマだけ変えて既存データはそのまま | 新規カラムでデフォルト値あり | NOT NULL 制約化の有無 |

### チェックリスト

- [ ] 既存データ件数を把握したか
- [ ] 移行戦略を選択した理由が明確か
- [ ] 移行中の **アプリ動作** が担保されているか（中間状態）
- [ ] 切り戻し手順が用意されているか
- [ ] 移行のドライランを検証環境で計画したか
- [ ] 関連テーブルの参照整合性に影響がないか
- [ ] バックアップ戦略を確認したか

## 例示シナリオ集（複数パターンで学ぶ）

> 影響範囲分析は様々な改修種別に適用できる。代表的な 4 シナリオで「3 層をどう埋めるか」のイメージを示す。

### シナリオ A：ステータス値の追加

| 層 | アクション |
|---|---|
| 参照層 | ステータス列挙型の全使用箇所を機械的に抽出 |
| 状態層 | 状態遷移マトリクスに新行・新列を追加し、矛盾遷移を排除 |
| データ層 | 既存レコードのうち新ステータスに該当するものの判定／移行要否 |

### シナリオ B：API エンドポイント追加

| 層 | アクション |
|---|---|
| 参照層 | 利用するサービス層・リポジトリ層のシンボル参照（呼び出し元の追加位置） |
| 状態層 | API が状態遷移を引き起こすか／既存遷移との整合 |
| データ層 | 新規データの永続化先・既存テーブルへの追記／別テーブル化判断 |

### シナリオ C：外部サービス連携の追加

| 層 | アクション |
|---|---|
| 参照層 | 連携クライアントのシンボル参照／設定値の参照箇所 |
| 状態層 | 連携結果による状態遷移／タイムアウト・エラー時の状態 |
| データ層 | 連携結果の保存先／冪等性キーの保存／重複検知 |

### シナリオ D：スキーマ変更を伴うデータ移行

| 層 | アクション |
|---|---|
| 参照層 | 変更カラムの全参照（SQL／オブジェクトリレーショナルマッピング／レポート） |
| 状態層 | 移行中のレコードが取り得る中間状態とその許容性 |
| データ層 | 移行戦略の選択／所要時間試算／切り戻し手順 |

## データ層の出力例（シナリオ A の場合）

```markdown
## データ層：「承認待ち」ステータス追加に伴う既存データ整合

### 既存データ件数
- 注文テーブル: 約 50 万件
- うち status = 'DRAFT' のレコード: 約 1 万件

### 移行戦略
- 採用: 段階的バックフィル
- 理由: 50 万件のうち実質変更が必要なのは 1 万件、サービス停止不可

### 中間状態でのアプリ動作
- アプリ側で「承認待ち」を扱える状態にデプロイ → 後続でバックフィル開始
- バックフィル中も既存 DRAFT は引き続き処理可能

### 切り戻し
- バックフィル前に DRAFT レコードを別テーブルにバックアップ
- 切り戻し時は status を DRAFT に戻すスクリプトを実行

### ドライラン
- 検証環境で同件数を生成し、所要時間を計測
```

## 影響範囲分析の出力テンプレート

```markdown
# <タスク名> 影響範囲分析

## 改修対象
<改修する機能・領域の概要>

## 参照層
<使用箇所の一覧と影響判定>

## 状態層
<状態遷移マトリクスと矛盾チェック結果>

## データ層
<移行戦略と既存データへの影響>

## 結論
- 影響範囲: <ファイル数・テーブル数>
- 必要な作業: <列挙>
- リスク: <高・中・低 + 内容>
- 採用する戦略: <概要>

## レビュアーへの問い
- 参照層の網羅は十分か（リフレクション等の見落としがないか）
- 状態層のマトリクスに矛盾遷移がないか
- データ層の戦略はサービス継続性を担保するか
```

## よくある失敗

| 失敗 | 起きる層 | 対策 |
|---|---|---|
| 全文検索だけで参照を洗い、リフレクションを見落とす | 参照層 | リフレクション・動的呼び出しの有無を独立に確認する |
| 状態遷移マトリクスを「埋めなくていいセル」で空欄にする | 状態層 | 全セル埋めるルール |
| 移行を「あとで考える」で先送りにする | データ層 | 影響設計レビューの必須項目に含める |
| 切り戻し手順を書かない | データ層 | テンプレートに必須項目として組み込む |
| 「3 層すべて該当なし」を口頭判断のみで進める | 全層 | Gate 1 への明示記載で抜け漏れを防止 |
