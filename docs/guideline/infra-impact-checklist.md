# インフラ影響チェックリスト

改修時に **アプリ層だけでなくインフラ層への影響** を見落とさないためのチェックリスト。

> **使い方**: [workflow.md](workflow.md) の「ステップ 3：影響設計」で、[impact-analysis.md](impact-analysis.md) と並行して実施する。

---

## なぜ必要か

影響範囲分析（参照層／状態層／データ層）はアプリ層の整合性を見るが、インフラ層の影響は別観点である。

- 「コードは正しいが、本番のタイムアウトに引っかかる」
- 「テストでは通ったが、本番のデータ量でメモリ不足になる」
- 「新規外部サービス連携が、本番からは到達できない」
- 「データ移行がロックを取り続けて他処理が止まる」

これらはアプリのコードレビューでは見えない。**機械的なチェックリスト** で潰す。

---

## チェックカテゴリ

### A. 処理時間・タイムアウト

- [ ] 大量データを扱う処理がタイムアウト内に終わるか試算したか
- [ ] HTTP リクエストの場合、ロードバランサ・APIゲートウェイのタイムアウト上限内か
- [ ] 同期処理で長時間処理を行っていないか（非同期化検討）
- [ ] バッチ処理の所要時間が次回起動間隔を超えないか
- [ ] 想定最大データ量での処理時間試算をしたか（現在量だけでなく将来量）

### B. 外部サービス連携・通信

- [ ] 新規に呼び出す外部サービスがあるか
  - [ ] 本番環境からの到達性（ファイアウォール・許可リスト）を確認したか
  - [ ] レート制限を確認したか
  - [ ] 認証情報の管理方法を決めたか（機密情報管理サービス等）
  - [ ] タイムアウト・リトライ・サーキットブレーカーを設定したか
  - [ ] エラー時のフォールバック動作を決めたか
- [ ] 既存外部サービスの呼び出し回数・パターンが変わるか
  - [ ] レート制限超過リスクはないか
  - [ ] 課金影響はないか

### C. データストア・スキーマ移行

- [ ] スキーマ変更がある場合、移行戦略を [impact-analysis.md](impact-analysis.md) のデータ層で確定したか
- [ ] 移行中の **ロック時間** を見積もったか
- [ ] 移行中も **アプリが動作可能** か（中間状態の互換性）
- [ ] インデックス追加・削除の **本番影響時間** を見積もったか
- [ ] 切り戻し手順を用意したか
- [ ] バックアップ取得を計画したか
- [ ] ドライランを検証環境で計画したか

### D. バッチ・非同期処理

- [ ] 新規バッチ・非同期処理を追加するか
  - [ ] 起動方式（定期実行 / イベント駆動 / 手動）を決めたか
  - [ ] 多重起動防止の仕組み（ロック・分散ロック）を設計したか
  - [ ] 失敗時のリトライ戦略を決めたか
  - [ ] 失敗の検知・通知を設計したか
  - [ ] 実行ログ・監査ログを残す設計か
- [ ] 既存バッチ・非同期処理が影響を受けるか
  - [ ] 処理対象データ量の変化は許容範囲か
  - [ ] 実行時間の変化は許容範囲か

### E. リソース（CPU / メモリ / ストレージ / 帯域）

- [ ] CPU 使用率の増加見積もりをしたか
- [ ] メモリ使用量の増加見積もりをしたか（メモリ不足リスク）
- [ ] ストレージ使用量の増加見積もりをしたか
- [ ] ネットワーク帯域への影響を見積もったか
- [ ] 想定ピーク時の挙動を確認したか

### F. 可用性・障害許容

- [ ] 単一障害点を増やしていないか
- [ ] 障害時の影響範囲が明確か
- [ ] 既存のサービスレベル目標を維持できるか
- [ ] 障害復旧手順（運用手順書）を更新したか

### G. セキュリティ・認証認可

- [ ] 新規エンドポイントに認証認可を設定したか
- [ ] 新規外部通信が暗号化されているか
- [ ] 機密情報を環境変数・機密情報管理サービス経由で管理しているか
- [ ] ログに機密情報が出力されていないか
- [ ] 管理用エンドポイントの公開制御を確認したか
- [ ] 監査ログの記録対象に新規操作を含めたか

### H. 監視・ロギング・アラート

- [ ] 新規メトリクスを追加するか
- [ ] 新規エラーパターンに対するアラートを設定したか
- [ ] ログ保持期間が要件を満たすか
- [ ] ログ出力レベルが本番で適切か（過剰／不足）
- [ ] 分散トレーシング対応が必要か

### I. デプロイ・リリース

- [ ] 設定ファイルの変更があるか（環境変数の追加等）
- [ ] 環境ごとに設定差異があるか（開発／検証／本番）
- [ ] フィーチャーフラグの利用を検討したか
- [ ] カナリアリリース・段階リリースを検討したか
- [ ] 切り戻し手順が用意されているか
- [ ] デプロイ順序（データストア → アプリ → 外部設定）を確定したか

### J. 互換性・依存関係

- [ ] 依存ライブラリのバージョン変更があるか
- [ ] **依存ライブラリの新規追加判断**（後述 J.1 を参照）
- [ ] 既存 API の破壊的変更があるか（クライアントへの影響）
- [ ] 上流・下流システムへの影響を確認したか
- [ ] 既存データとの後方互換性を確認したか

#### J.1 依存ライブラリの新規追加判断

新規ライブラリ・フレームワークの採否判断は **Gate 1 段階で確定** する（実装着手後の判断は禁止）.
判断結果はアーキテクチャ判断記録（ADR: Architecture Decision Record）として残し、Gate 1 議事メモから参照する.

| 確認項目 | 内容 |
|---|---|
| 採否判断のタイミング | **Gate 1 通過前**（影響設計レビューに含む）|
| ADR の起票タイミング | Gate 1 通過と同時、または直前 |
| 確認内容 | (1) 既存技術スタックとの互換性 (2) 公式サポート状況 (3) ライセンス (4) セキュリティ評価 (5) 代替選択肢との比較 |
| 採用しない理由の記録 | 必須（[test-strategy.md](test-strategy.md) と [security-policy.md](security-policy.md) でも採用される「採用しない理由を必ず書く」原則に従う）|

ADR の配置・テンプレートは [document-plan.md](document-plan.md) を参照する.

## チェック結果のテンプレート

```markdown
# インフラ影響チェック — <タスク名>

## 該当項目
- [x] B. 外部サービス連携（新規呼び出し）
- [x] C. データストア・スキーマ変更
- [x] H. 監視（新規メトリクス）

## 詳細

### B. 外部サービス連携
- 連携先: <例: 認証サービス>
- 到達性: 本番ファイアウォール許可申請済（管理票 #XXXX）
- レート制限: 100 リクエスト/秒、想定 10 リクエスト/秒で問題なし
- 認証情報: 機密情報管理サービス経由
- タイムアウト: 3 秒、リトライ 2 回
- フォールバック: 認証失敗時はログイン画面にエラー表示

### C. データストア・スキーマ変更
- 変更内容: 注文テーブルに status='APPROVAL_WAITING' 追加
- 移行戦略: 段階的バックフィル
- ロック時間: スキーマ変更で約 30 秒見積もり、メンテナンス枠で実施
- 切り戻し: バックフィル前のスナップショット取得

### H. 監視
- 新規メトリクス: 認証サービス呼び出し成功率
- アラート: 成功率 99% 未満で警告

## リスク評価
- 高リスク項目: なし
- 中リスク項目: 移行中のロック（メンテナンス枠で対応）
- 低リスク項目: その他

## レビュアーへの問い
- 認証失敗時のフォールバック動作は妥当か
- メンテナンス枠の取得タイミングは妥当か
```

## 該当なし時の運用

すべての項目が「該当なし」の場合でも、**該当なしの宣言を残す**。チェックリストを回したことの証跡になる。

```markdown
# インフラ影響チェック — <タスク名>

## チェック結果
すべての項目で「該当なし」を確認。

## 確認した観点
- A. 処理時間: 既存処理の延長で、追加計算は軽微
- B. 外部サービス連携: 新規呼び出しなし
- C. データストア・スキーマ: 変更なし
- ...
```
