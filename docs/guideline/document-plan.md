# ドキュメント計画テンプレート

「いつ・何を・誰が」書くかを **最初に決める** ことで、ドキュメントが後回しになり腐るのを防ぐ。

> **使い方**: プロジェクト初期セットアップ時、または [workflow.md](workflow.md) の「ステップ 3：影響設計」で本テンプレートに従い計画を確定する。タスク完了条件にドキュメント更新を **必ず含める**。

---

## ドキュメント種別と作成タイミング

> ドキュメントの分類粒度・配置先（リポジトリ内のディレクトリ、社内 Wiki、Confluence スペース等）は各プロジェクトで自由に決める。

| ドキュメント | 内容 | 作成タイミング | 更新タイミング |
|---|---|---|---|
| **アーキテクチャ判断記録**<br/>（ADR: Architecture Decision Record） | 技術判断の記録 | 技術選定時 | 判断見直し時（追記、過去版は残す） |
| **API 仕様書** | エンドポイント定義 | API 追加タスクごと | API 変更時 |
| **状態遷移図** | ステートマシン定義 | 状態追加タスクごと | 状態変更時 |
| **アーキテクチャ図** | システム全体構造 | アーキテクチャが固まったタスクで最初に作成 | 構造変更時 |
| **データモデル図** | データ実体と関係 | データモデルが固まったタスクで最初に作成 | スキーマ変更時 |
| **画面仕様** | 画面要素・遷移 | 画面追加タスクごと | UI 変更時 |
| **データ定義** | テーブル・カラム定義 | スキーマ追加時 | スキーマ変更時 |
| **セキュリティ方針** | 認証認可・脅威モデル（テンプレート: [security-policy.md](security-policy.md)） | プロジェクト初期セットアップで初版 | 方針変更時 |
| **テスト戦略** | 品質特性ベース戦略 | プロジェクト初期セットアップで初版 | 戦略見直し時 |
| **運用手順書** | 障害対応・定常運用 | 運用開始前 | 障害対応経験ごと |
| **議事メモ** | 方針合意・相談記録 | 意思決定時 | 都度 |

## ドキュメント計画の決定テンプレート

```markdown
# ドキュメント計画 — <プロダクト名>

## 必須ドキュメント
- [ ] アーキテクチャ判断記録: 技術選定時に作成
- [ ] API 仕様書: API 追加タスクごと
- [ ] 状態遷移図: 状態追加タスクごと
- [ ] セキュリティ方針: プロジェクト初期セットアップで初版作成（[security-policy.md](security-policy.md) のテンプレートを利用）
- [ ] テスト戦略: プロジェクト初期セットアップで初版作成
- [ ] アーキテクチャ図: アーキテクチャが固まったタスクで最初に作成
- [ ] データモデル図: データモデルが固まったタスクで最初に作成

## 任意ドキュメント（必要に応じて）
- [ ] 画面仕様: 画面が複雑な場合
- [ ] 運用手順書: 本番運用前
- [ ] データ定義書: データモデル図で不足する場合

## 配置先

各プロジェクトで決める（リポジトリ内のディレクトリ、社内 Wiki、Confluence 等）。

## 形式ルール
- 言語: 日本語（または各チームの公用語）
- 図: テキスト管理可能な記法を優先（Mermaid 等）
- 出典: 既存コード参照は `path:line`、外部資料は URL + 取得日

## 更新義務
- タスク完了条件にドキュメント更新を必ず含める
- ドキュメント未更新のままタスク完了にしない（検証エージェントが不合格を出す）

## レビュー周期
- アーキテクチャ判断記録: 半年に 1 回、判断が現状に合っているかレビュー
- セキュリティ方針: 半年に 1 回、または重要なリリース前にレビュー
- テスト戦略: 半年に 1 回、または重要なリリース前にレビュー
```

## アーキテクチャ判断記録テンプレート

```markdown
# NNNN: <判断タイトル>

- **日付**: YYYY-MM-DD
- **ステータス**: 提案中 / 承認済 / 廃止 / 置換（NNNN による）
- **決定者**: <ロール / 個人>

## コンテキスト
<判断が必要になった背景・制約・課題>

## 検討した選択肢

### 選択肢 A: <概要>
- メリット: ...
- デメリット: ...

### 選択肢 B: <概要>
- メリット: ...
- デメリット: ...

## 決定
**選択肢 X を採用する。**

## 理由
<採用理由・棄却理由>

## 影響
- ポジティブ: ...
- ネガティブ: ...
- 既知のリスク: ...

## 関連
- 関連判断記録: NNNN
- 関連ドキュメント: <リンク>
```

## 各ドキュメント記述時の必須要素

すべてのドキュメントに以下を含める。

| 要素 | 内容 |
|---|---|
| **目的** | このドキュメントが解決する問い |
| **対象読者** | 誰が読むか（チーム全員／開発者のみ／運用担当 等） |
| **更新履歴** | 末尾に日付・版・変更者・内容のテーブル |
| **出典** | 参照元（コード `path:line`、外部 URL + 取得日） |

## ドキュメントが腐らないための運用

| ルール | 効果 |
|---|---|
| タスク完了条件にドキュメント更新を含める | 「あとで書く」を発生させない |
| 検証エージェントがドキュメント整合性を必ず目視確認（自動検出できないため） | 更新漏れを検出 |
| workflow の「ステップ 1：把握・整理」でドキュメント↔コード乖離をチェック | 改修前に乖離を解消 |
| 古い情報には「廃止」と明記して残す | 履歴が追える／消すと判断理由が失われる |
| 同じ情報を複数箇所に書かない | 片方の更新漏れで矛盾が発生する |

---

## やってはいけないパターン

| 不適切 | 理由 | 代替 |
|---|---|---|
| 後でまとめて全部書く | 記憶を頼りに書く＝抜け漏れ確実 | タスクごとに更新 |
| コードコメントだけで完結させる | 横断的な仕様が見えない | 仕様はドキュメント、コメントは「なぜ」だけ |
| 古い情報を黙って削除する | 「なぜ変えたか」が失われる | 廃止と明記して残す or 判断記録に履歴 |
| 同じ情報を複数箇所に書く | 必ず片方が腐る | 一次情報源を決め、他は参照リンク |
