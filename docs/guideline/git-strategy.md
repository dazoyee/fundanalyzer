# Git 戦略

ブランチ・コミット・マージ運用を **チーム共通の規約** として定める。AI エージェントを含む 3 + N 体制で開発する以上、Git 履歴は「機械が生成した結果を人間が責任を持って統合した記録」であり、レビューと監査の一次資料となる。

> **使い方**: 本書は **規約型** のガイドラインとして、推奨デフォルトを 1 つだけ提示する。逸脱する場合は **逸脱の理由をプロジェクト内のドキュメント（アーキテクチャ判断記録 等）に残す** こと。
> プロジェクト初期セットアップ時に本書の内容を確認し、逸脱が必要な場合のみ判断記録を作成する。

> **スコープ外**: コードレビュー手段（プルリクエスト・マージリクエスト・パッチメール・ペアレビュー等）は本書では規定しない。レビュー運用は [human-checkpoints.md](human-checkpoints.md) と [roles.md](roles.md) に委ねる。

---

## 推奨デフォルト一覧

| 観点 | 推奨デフォルト |
|---|---|
| ブランチ戦略 | **主ブランチ常時リリース可能型 ＋ 短命作業ブランチ**（複数モデルから選択可） |
| ブランチ命名 | `<種別>/<簡潔な内容>` 例: `feature/order-status`, `fix/login-redirect` |
| コミットメッセージ構造 | **3 層構造**（要約・本文・フッタ） |
| コミット本文の方針 | **「なぜ」を書く**（「何を」は差分で読める） |
| メッセージ規約の代表例 | **Conventional Commits**（`<type>: <要約>`） |
| コミット粒度 | **1 タスク = 1 コミット**（タスクサイクルとの 1:1 対応） |
| マージ方式 | **Squash Merge**（主ブランチは 1 タスク = 1 コミットの履歴に保つ） |
| コミット前レビュー | コミット操作の前に人間が差分レビュー（Gate 2）／合格してからコミット |
| AI 帰属表記 | Co-Authored-By フッタで明示／人間レビュー必須 |
| 履歴保護 | 共有ブランチへの強制 push 禁止／公開済みコミットの改変禁止 |

逸脱時はプロジェクト内のアーキテクチャ判断記録に「採用しない理由」と「代替戦略」を記す。

## 1. ブランチ戦略

### 1.1 共通の最小要件（モデル非依存）

どのブランチモデルを選んでも、以下は共通して満たすこと。

- **主ブランチ**（`main` / `master` / `trunk` 等）は **常時リリース可能** な状態を保つ
- 機能・修正は **作業ブランチ** で行い、主ブランチに直接 push しない
- 作業ブランチは **短命**（数日〜1 週間が目安）で、マージ後は削除する
- 主ブランチへの取り込みは **コードレビューを経る**（手段は問わない／[human-checkpoints.md](human-checkpoints.md) Gate 2 通過後）

### 1.2 ブランチモデルの選択肢

代表的な 3 モデルを並列に示す。プロジェクトの規模・リリース頻度・並行リリース要件に応じて選び、選択結果をアーキテクチャ判断記録に残す。

| モデル | 主な構成 | 向いている用途 |
|---|---|---|
| **主ブランチ運用型** | 主ブランチ ＋ 短命作業ブランチ | 単一リリース系統・継続的デリバリー |
| **フロー型** | 主ブランチ ＋ 開発ブランチ ＋ 機能・リリース・修正ブランチ | 並行リリース・長期サポート版あり |
| **トランクベース開発型** | 主ブランチ中心・極短命作業ブランチ（数時間〜1 日） | 高頻度デプロイ・小規模変更主体 |

> モデル名は業界で複数の流派が存在する（GitHub Flow / Git Flow / Trunk-Based Development 等）。固有名はホスティングサービスや書籍に紐づく場合があるため、本書では **構成上の特徴で識別** する。各プロジェクトでは固有名と対応関係を判断記録に残してよい。

### 1.3 ブランチ命名規約

```
<種別>/<簡潔な内容>
```

| 種別 | 用途 | 例 |
|---|---|---|
| `feature` | 新機能追加 | `feature/order-status` |
| `fix` | バグ修正 | `fix/login-redirect` |
| `refactor` | 挙動を変えないリファクタリング | `refactor/order-service` |
| `docs` | ドキュメントのみの変更 | `docs/architecture-update` |
| `test` | テスト追加・修正のみ | `test/order-coverage` |
| `chore` | ビルド・補助ツール変更 | `chore/dep-update` |

### 1.4 ブランチ運用ルール

- 作業ブランチは **主ブランチから派生** する（他の作業ブランチから派生させない）
- 主ブランチの最新を取り込むときは **Rebase または Merge** を使う（プロジェクトで統一する）
- 作業ブランチ上での履歴整理（インタラクティブリベース・amend）は **公開前** に限り許容
- 共有後（push 後・他者がチェックアウト後）の履歴改変は禁止

## 2. コミット戦略

### 2.1 1 タスク = 1 コミット原則

[workflow.md](workflow.md) のタスクサイクル 1 周（1 タスク）と、主ブランチに残るコミットを **1:1 で対応** させる。

- タスク完了 = 「機能 + テスト + ドキュメント」3 点セットが揃った状態
- 実装途中のコミット（中間コミット）は **作業ブランチ上では許容**、主ブランチには **Squash Merge で 1 コミットに集約**（[§4](#4-マージ戦略)）
- 1 コミットでスコープを跨がない（[workflow.md](workflow.md) のスコープ確定区分「コア／後回し／対象外」を超えない）

### 2.2 コミットメッセージの必須構造（3 層構造）

業界一般のコミットメッセージは「要約・本文・フッタ」の 3 層で構成される。本書はこの構造を **必須** とする。

```
<要約（1 行目）>

<本文（任意・複数段落可）>

<フッタ（任意・複数行可）>
```

| 層 | 必須 | 内容 |
|---|---|---|
| **要約**（1 行目） | ✅ 必須 | 変更内容を一文で表す。**50 文字以内**（多言語環境では文字数の目安）／命令形の現在形（「〜する」「〜を追加」）／末尾にピリオドを付けない |
| 空行 | ✅ 必須（本文・フッタを書く場合） | 1 行目と本文の区切り |
| **本文** | ⭕ 推奨（自明な変更を除き必須） | **「なぜ」変更したかを書く**（「何を」は差分で読める）。背景・制約・代替案の検討結果・影響範囲などを記す |
| **フッタ** | △ 任意 | 関連タスク／課題番号・破壊的変更（`BREAKING CHANGE: <内容>`）・共著者（`Co-Authored-By: ...`）等 |

### 2.3 「なぜ」を書く理由

差分（diff）は「何を変えたか」を機械的に表現できるが、「なぜ変えたか」は失われる。半年後・1 年後に履歴を読む者は、当時の議論・制約・棄却された選択肢を本文から読み取る。

| 観点 | 書くべき例 |
|---|---|
| 背景 | 「利用者から〇〇のクレームが多発したため」 |
| 制約 | 「外部 API のレート制限に対応するため」 |
| 代替案 | 「キャッシュ追加も検討したが、データ鮮度要件により採用しなかった」 |
| 影響 | 「既存利用者には影響なし／本変更により〇〇が変わる」 |

### 2.4 メッセージ規約の代表例：Conventional Commits

要約に **type prefix** を付ける規約として **Conventional Commits**（`<type>: <要約>`）が広く使われている。本書では **採用を必須としない** が、type による分類はリリースノート自動化・履歴の検索性向上に有効なため、代表例として推奨する。

#### type の代表例

| type | 用途 |
|---|---|
| `feat` | 新機能追加（利用者から見える動作の追加） |
| `fix` | バグ修正 |
| `refactor` | 挙動を変えない内部構造の改善 |
| `test` | テストの追加・修正のみ |
| `docs` | ドキュメントのみの変更 |
| `chore` | ビルド・補助ツール・依存更新等 |
| `perf` | 性能改善（挙動は不変、計測値を本文に記す） |
| `revert` | 過去コミットの取り消し |

#### 採用例

```
feat: 注文ステータスに「承認待ち」を追加

承認フロー導入のため、下書きと公開済みの間に承認待ち状態を追加する。
既存「下書き」レコードは移行スクリプトで影響を受けない。

Refs: TASK-1234
Co-Authored-By: <AI エージェント名> <noreply@example.com>
```

#### 別の規約（gitmoji 等）を採用する場合

絵文字 prefix（gitmoji 等）や独自 prefix を採用してもよい。ただし **3 層構造** と **「なぜ」を書く** は共通の必須要件として守る。プロジェクトで規約を選んだら、判断記録に残す。

### 2.5 悪い例（要約のみ）

```
update                        # 何を更新したか不明
fix bug.                      # 要約が抽象的・末尾ピリオド
WIP                           # 共有ブランチに残してはならない
.                             # 内容なし
```

### 2.6 AI エージェントが生成したコミットの取扱い

本ガイドラインは AI エージェント（計画／実装／検証）を前提とする。AI 生成コードを含むコミットは **必ず明示する**。

#### 必須要件

- フッタに `Co-Authored-By: <AI エージェント名 / モデル識別子> <noreply@example.com>` を記載
- **コミット操作の前に [§3 コミット前レビュー（Gate 2）](#3-コミット前レビューgate-2) を通過** していること
- コミット主は **人間レビュア** または人間が承認した実装担当（コミット権限は人間のみ）

#### 禁止事項

- AI が生成したコミットメッセージを **無検証でコミット** する
- AI 帰属を **意図的に隠す**（人間が単独で書いたかのように記す）
- AI が **Gate 2 未通過のまま** コミットする

> コミットの正当性・履歴の妥当性は人間が判断する（コア原則は [human-checkpoints.md](human-checkpoints.md) を一次情報源とする）.

### 2.7 コミット粒度の判定

| 状況 | 判定 |
|---|---|
| 機能追加とリファクタリングが混在 | 分けてコミット（レビュー困難になる） |
| 同一機能の複数ファイル修正 | 1 コミットに集約 |
| ドキュメント更新と実装変更 | 同じタスクで生じたものは 1 コミット |
| 機能追加とリファクタリングが混在 | 分けて別コミット（レビュー困難になる）／別タスクに分離検討 |
| 偶然見つけた無関係なバグ修正 | 別コミット・別タスクに分離 |

## 3. コミット前レビュー（Gate 2）

[human-checkpoints.md](human-checkpoints.md) の **Gate 2 を「コミット操作の前」に位置付ける**。

### 3.1 フロー

1. 実装エージェントが変更を完了する（ファイル編集まで／**まだコミットしない**）
2. 作業ツリーの差分・実機動作確認結果・副次影響・ドキュメント整合性を人間に提示する
3. 人間が Gate 2 として合否を判定する
4. **合格** → 実装エージェント（または人間）がコミット
5. **不合格** → 修正してから再レビュー（合格するまでコミットしない）

### 3.2 コミット前レビューを採用する理由

- **コミット履歴を最初から正にする**：未レビューのコミットを後から amend / リバートする手間を排除する
- **AI 生成コードに対する人間判断を必ず介在させる**：AI が単独でコミット履歴を生成する状況を構造的に防ぐ
- **1 タスク = 1 コミット原則を支える**：レビュー単位とコミット単位を一致させる

### 3.3 コミット前に満たすべき条件

| 条件 | 内容 |
|---|---|
| **継続的インテグレーション（CI）相当の確認** | 静的解析・テストがローカルで成功している |
| **実装作業後の検証** | [workflow.md](workflow.md) のステップ 5 が合格 |
| **Gate 2（コミット前レビュー）** | [human-checkpoints.md](human-checkpoints.md) の通過記録あり |
| **コミットメッセージ整形** | 3 層構造・Conventional Commits・AI 帰属フッタが整っている |

> CI を別途回す運用（push 後にリモート CI で確認）も妨げない。その場合でも push 前に Green を確認することを推奨する。

## 4. マージ戦略

### 4.1 推奨：Squash Merge

主ブランチへの取り込みは **Squash Merge** を推奨する。

- 1 作業ブランチ = 1 タスク = 1 コミット の対応が主ブランチの履歴で保たれる
- 作業ブランチ上の中間コミットは主ブランチに残らない
- リバート時の単位が明確（1 タスク単位で取り消せる）

### 4.2 マージコミットメッセージ

Squash Merge 時のメッセージは、[§2.2](#22-コミットメッセージの必須構造3-層構造) の 3 層構造に従って書き直してから取り込む。作業ブランチ最終コミットや作業中メモをそのまま採用しない。

### 4.3 取り込み前の必須条件

| 条件 | 内容 |
|---|---|
| **継続的インテグレーション（CI）** | 静的解析・テストがすべて成功している |
| **コードレビュー** | レビュー手段は問わない（[human-checkpoints.md](human-checkpoints.md) に委ねる） |
| **実装作業後の検証** | [workflow.md](workflow.md) のステップ 5 が合格 |
| **Gate 2** | [human-checkpoints.md](human-checkpoints.md) の通過記録あり |

### 4.4 逸脱が許される代表例

- 長期にわたる作業ブランチで、中間コミットの履歴を残したい場合 → **Merge Commit**（`--no-ff`）を採用
- 線形履歴を厳格に保ちたい場合 → **Rebase Merge** を採用

逸脱する場合はプロジェクト内のアーキテクチャ判断記録に方針を記す。

## 5. 禁止操作（強制ルール）

以下は **逸脱を許可しない** 強制ルール。

| 操作 | 理由 |
|---|---|
| 共有ブランチへの **強制 push**（`push --force`） | 共有履歴の破壊・他者の作業消失 |
| `--no-verify` での **フックスキップ** | 静的解析・テスト・コミットメッセージ検証の回避 |
| 公開済みコミットの **`--amend`** | 共有履歴の暗黙改変・他者ローカルとの不整合 |
| **シークレットを含むファイル**（API キー・パスワード・個人情報・環境固有設定）のコミット | 漏洩リスク・取り消し困難 |
| AI 生成コードを **Gate 2 未通過のまま** コミット | 品質ゲート（CI・検証エージェント・人間レビュー）の意味喪失 |
| 巨大バイナリ・依存成果物（依存パッケージのインストール先ディレクトリ等）のコミット | リポジトリ肥大・履歴汚染 |

これらに違反するコミットは **主ブランチに取り込まない**。違反を発見した場合はリバートし、原因を再発防止策として記録する（[human-checkpoints.md](human-checkpoints.md) のスキップ違反運用に準じる）。

## 6. 受け入れチェックリスト

タスク完了時、コミット・ブランチが以下を満たしていることを確認する。

### コミット
- [ ] 1 タスク = 1 コミット原則に従っている（中間コミットは Squash で集約）
- [ ] 要約・本文・フッタの 3 層構造になっている（自明な変更を除き本文あり）
- [ ] 本文に **「なぜ」** が書かれている
- [ ] 要約は 50 文字以内・命令形・末尾ピリオドなし
- [ ] AI エージェントが関与した場合 Co-Authored-By を記載
- [ ] スコープを跨いでいない（コア／後回し／対象外を混在させない）
- [ ] シークレット・巨大バイナリを含まない

### レビュー
- [ ] コミット操作の **前に** Gate 2（差分レビュー）を通過している
- [ ] CI 相当の確認（静的解析・テスト）が合格している

### ブランチ
- [ ] 命名規約に従っている（`<種別>/<内容>`）
- [ ] 主ブランチから派生している
- [ ] 短命（マージ後すぐ削除予定）

## 7. 用語

| 用語 | 意味 |
|---|---|
| **主ブランチ** | リリース可能な状態を常時保つブランチ（`main` / `master` / `trunk` 等） |
| **共有ブランチ** | 複数人が参照・取り込みを行うブランチ（主ブランチを含む） |
| **作業ブランチ** | 機能・修正のために主ブランチから派生する短命ブランチ |
| **コミット前レビュー** | コミット操作の前に人間が作業ツリーの差分を確認する手続き。本書では Gate 2 がこれに該当 |
| **3 層構造** | コミットメッセージを「要約・本文・フッタ」に分ける業界一般の構造 |
| **Conventional Commits** | `<type>: <要約>` 形式のコミットメッセージ規約。type プレフィックスでコミット種別を表す |
| **Squash Merge** | 作業ブランチの全コミットを 1 つに圧縮して主ブランチに取り込む方式 |
| **Rebase Merge** | マージコミットを作らず、線形履歴を保つ取り込み方式 |
| **Merge Commit**（`--no-ff`） | 必ずマージコミットを作成し、ブランチ履歴を残す方式 |
| **強制 push**（`push --force`） | リモートブランチの履歴を上書きする操作。共有履歴を破壊する |
| **`--amend`** | 直前のコミットを書き換える操作。公開後は履歴改変となるため禁止 |
| **`--no-verify`** | コミット・push 時のフックを回避する操作。品質ゲートのバイパスに当たる |
| **Co-Authored-By** | コミットフッタで共著者を明示する標準形式 |
| **タスクサイクル** | [workflow.md](workflow.md) で定義する 5 ステップの単一サイクル |
