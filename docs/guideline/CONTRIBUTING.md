# CONTRIBUTING

本フレームワーク（`docs/guideline/`）を **更新する際の内部規約** を定める。各ファイルの内容自体ではなく、フレームワークそのものの **メンテナンス品質** を担保するための取り決めである。

対象は本リポジトリの `docs/guideline/` 配下を変更する PR。技術規約集側の更新規約は [`../tech-guideline/CONTRIBUTING.md`](../tech-guideline/CONTRIBUTING.md) を参照。

> 本フレームワークは [`README.md`](README.md) の方針に従い、温度感ラベル（規約 / 推奨 / 候補 / ガイド）を **付与しない**。強制度は本文中の **★必須・スキップ不可** / **△推奨・条件付き省略可** で表現する。

## 1. レビュー観点

PR を作成・レビューする際に **以下 3 観点** を確認する。各観点のチェックリストはレビュアーと PR 作成者の双方が見て使う。

### 1.1 内容（フレームワーク定義の妥当性）

- [ ] ★必須: 追加・変更する運用ルールが [`README.md`](README.md) の **コア原則 5 つ** と矛盾しないか
- [ ] ★必須: **タスクサイクル（5 ステップ）** ／ **3 + N 体制** ／ **Gate 1 / 2** の定義に逸脱がないか
- [ ] ★必須: **検証 5 観点**（コード品質 / テスト構造 / 機能完全性 / セキュリティ / ドキュメント整合性）の記述は [`README.md`](README.md) を一次情報源として参照しているか
- [ ] ★必須: **品質設計の三本柱**（テスト戦略 / セキュリティ方針 / ドキュメント計画）と検証 5 観点の関係を崩していないか
- [ ] △推奨: サンプル Markdown 骨格やテンプレートは [`human-checkpoints.md`](human-checkpoints.md) の **タスク 1 Markdown ファイル統合方式** と整合しているか
- [ ] △推奨: 外部の品質モデル（ISO/IEC 25010 等）を参照する場合、参照先と引用箇所が明示されているか
- [ ] △推奨: 「AI エージェントを使わないタスクには適用しない」という適用範囲を意図せず広げていないか

### 1.2 整合性（10 ファイル相互参照・Gate / 用語の一貫性）

本フレームワークは 10 ファイルが密に参照し合う構造のため、以下を必ず確認する。

- [ ] ★必須: **相対リンク**（`[xxx.md](xxx.md)` 形式）が現存パスを指しているか
- [ ] ★必須: **用語の表記** が [`README.md` §用語](README.md#用語) と一致しているか（Gate / タスクサイクル / 3 + N 体制 / 一次情報源 / ADR 等）
- [ ] ★必須: **Gate 1（設計の承認）/ Gate 2（最終確認）** の役割・通過条件・スキップ可否は [`human-checkpoints.md`](human-checkpoints.md) を一次情報源として参照しているか
- [ ] ★必須: **役割定義**（計画 / 実装 / 検証エージェント）の責務分担が [`roles.md`](roles.md) と矛盾していないか
- [ ] ★必須: **ADR の一次情報源** は技術規約集側 [`../tech-guideline/templates/adr.md`](../tech-guideline/templates/adr.md) を指しているか（運用方針のみを agent-workflow 側で記述）
- [ ] △推奨: 章をまたぐ規約（例: 影響設計と Gate 1）の **役割分担** が PR 後も明確か（重複が必要な場合は片方を「正本」と明示）
- [ ] △推奨: アンカー（`#section-xx`）を使う場合、対象見出しが現存しているか
- [ ] △推奨: テンプレート参照は同階層の `*.md` または `../tech-guideline/templates/` の正しいファイルを指しているか

### 1.3 セキュリティ

- [ ] ★必須: シークレット（API キー / パスワード / トークン）が直書きされていないか
- [ ] ★必須: **社内固有名**（人名 / サーバ名 / 内部 URL / プロジェクト識別子）が混入していないか
- [ ] △推奨: サンプル設定・YAML で実環境の接続先・認証情報が漏れていないか
- [ ] △推奨: 既存のセキュリティ規約（[`security-policy.md`](security-policy.md) 含む）を緩和する変更は要慎重レビューとなっているか

## 2. バージョニング規約

フレームワーク全体のバージョンは **SemVer**（`<MAJOR>.<MINOR>.<PATCH>`）で管理する。各 `.md` の末尾の **更新履歴** にバージョンと変更内容を記録する。

### 2.1 SemVer の bump 基準

| Bump | 該当ケース | 例 |
|---|---|---|
| MAJOR（`X.0.0`） | コア原則 5 つ・タスクサイクル本体・Gate 構造・3 + N 体制の **撤回 / 反転 / 根本変更** | タスクサイクルのステップ数を削減、Gate 1 を廃止、検証エージェントを廃止 |
| MINOR（`x.X.0`） | ファイル追加・既存ルールの拡張・テンプレート項目追加など、**後方互換を保つ拡張** | 検証観点を 1 つ追加、新規テンプレートファイルを追加 |
| PATCH（`x.x.X`） | 表記揺れ修正・誤字修正・リンク修正・整合性調整など、**運用レベルの変更を伴わない更新** | 用語の表記を統一、相対リンクのパスを修正 |

### 2.2 更新履歴の記載ルール

各 `.md` ファイルの **末尾** に下記フォーマットの表を置く。

```markdown
## 更新履歴

| 日付 | バージョン | 概要 |
|---|---|---|
| 2026-04-28 | 1.0.0 | 初版 |
```

- ★必須: 列構成は **日付 / バージョン / 概要** の 3 列とする。列の追加・削除は MAJOR レベルの変更
- ★必須: 概要は **1 文要約**（フェーズ名・コミットハッシュなど内部経緯は記載しない）
- ★必須: 1 PR で複数ファイルを変更した場合、**変更したファイルにのみ** 行を追加する（変更しないファイルの履歴は触らない）
- ★必須: バージョンは **昇順** で追記する（最新行を最下行に）
- △推奨: 同一日付・同一バージョンの行が複数ファイルに分散していてもよい（ファイルを跨いだ整合改修などで自然に発生する）

### 2.3 バージョン bump のタイミング

- ★必須: **PR 単位で bump はしない**。1 PR では既存バージョンに変更内容を追記してもよい
- △推奨: **論理マイルストーン**（例: 「検証エージェント責務整理完了」「Gate 運用見直し完了」など）でバージョンを上げる
- △推奨: バージョンを上げた PR の本文に、bump 理由と影響範囲を明記する

## 3. PR 作成・マージのフロー

PR フローは [`../tech-guideline/06-build-and-cicd/git-flow.md`](../tech-guideline/06-build-and-cicd/git-flow.md) に従う（本リポジトリは GitHub Flow を採用）。コミットメッセージ規約は [`git-strategy.md`](git-strategy.md) を一次情報源とする。本フレームワーク特有の追加事項のみ以下に示す。

- ★必須: タイトルは Conventional Commits 形式（`docs(agent-workflow): <変更内容>` を推奨）
- ★必須: 1 PR で複数ファイルにまたがる変更は、**ファイルごとにレビュー観点 3 つを確認** する
- △推奨: 大きな構成変更（ファイル追加・章再編・Gate 構造変更・コア原則変更）は事前に Issue / 議事メモで合意してから PR を作成する
